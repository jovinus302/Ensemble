# Ensemble MVP 범위

## 증명하려는 경험

여러 사람과 여러 Agent가 다양한 협업에서 일할 때 PM Agent가 흩어진 맥락을 목표 아래 연결하고 다음 행동을 조율한다. 제품의 지속적인 기준은 [intent.md](../intent.md)다.

## 현재 feasibility

기존 CLI connector와 PM Agent 런타임을 재사용한다. 목표 입력 → 계획과 결정 요청 → 승인 → CLI 작업 → 상태·산출물 확인이라는 작은 경로를 관찰한다. /demo는 이를 확인하는 대시보드이며 사람별 작업 환경을 복제하지 않는다. 실제 서버 기록만 표시하고 데이터가 없으면 빈 상태를 보여준다.

이 단계는 모든 도구 연동·운영 수준 완성도·조율 효과의 입증을 요구하지 않는다. 기존 앱이 관리하는 CLI 세션을 연결하며 임의의 개인 Agent 세션을 자동 수집하지 않는다. 실행 설정, 실행 성공, 산출물 제출, 검토 완료를 구분한다.

## 후속 도구 선택과 연결 가설

| 영역 | 첫 도구/접점 | 최소 검증 |
|---|---|---|
| 디자인 | [Figma 파일 댓글](https://github.com/jovinus302/Ensemble/issues/78) | 변경 맥락 하나를 읽고 확인 질문/다음 행동을 댓글로 연결 |
| 메신저 | [Slack App](https://github.com/jovinus302/Ensemble/issues/79) | @Ensemble 멘션 한 건에 같은 스레드로 답변 |
| 미팅 | [Google Meet + Calendar 참여·주선](https://github.com/jovinus302/Ensemble/issues/80) | 초대받아 입장·회의 중 확인, 방 생성·초대, 결정의 Space 기록. 회의록은 보조 입력. [실험 기록](feasibility/meeting-google-meet.md) |

도구 선택은 feasibility 가설이며 특히 회의 도구는 실제 사용 환경을 확인해야 한다. API 권한과 접근 가능성부터 확인하고 한 건의 왕복 또는 기록 연결로 검증한다. 디자인·Slack·미팅이 이미 연동됐다고 표현하지 않는다.

## 유지할 조건

원장·권한·중복 실행 방지·프로젝트 격리·오래된 결과 차단은 유지한다. 제안과 확정 결정을 구분하고 공유하지 않은 개인 작업을 자동 수집하지 않는다. UI 테스트나 fake 실행을 실제 CLI 연결 증거로 대체하지 않는다. 내부 계약은 [작업 모델](work-model.md), 실행 선택은 [아키텍처](mvp-architecture.md)를 따른다.

## 이후 검증

실제 팀의 재설명·수동 추적·누락·지연을 관찰하고 기존 방식과 비교한다. 조직 인증·보존 정책·다중 프로젝트 운영·다양한 협업별 판단 품질은 후속 범위다.
