# Ensemble MVP 범위

확인 기준: 2026-10-05, `main@605521b`의 구현과 이후 문서·데모 디렉토리 정리. 제품 방향은 [intent.md](../intent.md)가 기준이다. 코드가 있다는 이유로 사용자 가설이 입증됐다고 판단하지 않는다.

## 증명하려는 것

**사람이 자신의 Agent와 만든 결과를 공유했을 때, 필요한 검토를 유지하면서 재설명·수동 추적·인계 재작업을 줄일 수 있는가?** 사람은 개인 Agent와 직접 일하고, PM은 합의된 팀 업무와 공유 결과를 검토·의존성·후속 작업으로 연결한다. 모든 개인 작업이 PM의 배정으로 시작될 필요는 없다.

사람은 인터뷰·판단·협상·제작을 하는 팀원이다. 채널·공유 기억·검증·작업 기록은 다음 일을 잇기 위한 수단이다.

## 의도와 현재 구현

| 필요한 일 | 현재 구현 근거 | 확인할 경계 |
|---|---|---|
| 목표를 작업과 담당으로 연결 | [계획 제안·확인](../app/packages/orchestrator/src/planning.ts), 작업 계층·담당자 | 계획 생성 성공은 유용한 팀 구성이나 조율 부담 감소의 증거가 아님 |
| 사람과 Agent에게 맥락 전달 | 결정·제약·선행 결과·출처를 담는 [작업 맥락](../app/packages/orchestrator/src/context.ts) | 외부 채널 맥락 자동 수집은 구현 범위가 아님 |
| 결과 확인 후 다음 일 시작 | [인계 판단](../app/packages/orchestrator/src/handoff.ts), [dispatch](../app/packages/orchestrator/src/dispatch.ts), 보완·재개 | `checked`는 인계 판정. 일반 웹앱이 모든 결과를 자동 build/browser 검증하지 않음 |
| 대화의 결론을 계획과 담당자에게 반영 | [coordination](../app/packages/orchestrator/src/coordination.ts), 계획 버전·변경 전달·권한 요청 | 후속 메시지의 PM 판단 선점과 Agent steering은 별개 |
| 막힌 이유와 다음 행동 파악 | 결정 요청·작업 패널·정체 점검·하루 요약 | 실행 중인 서버의 점검이며 외부 상시 스케줄러는 아님 |
| 기한과 가용 시간에 근거한 조율 | [예측](../app/packages/core/src/forecast.ts), 가용 시간·작업 추정 | 입력 누락을 추정 사실로 채우지 않음. 예측 정확도는 실사용 검증 필요 |

실행 설정은 [아키텍처](mvp-architecture.md), 상세 계약은 [작업 모델](work-model.md)을 따른다. PM은 API·Codex·Claude·fake, 실행 Agent는 Codex·Claude·fake를 선택한다.

## 유지할 경계

- 승인·위임된 범위 안에서 일을 잇는다. 대화나 침묵을 자동 승인으로 바꾸지 않는다.
- 사람의 새로운 시간 약속과 역할·일정 변경에는 해당 사람의 의사가 필요하다.
- 실행 Agent는 원장을 직접 쓰거나 담당·권한을 바꾸지 않는다.
- 예약과 Agent 점유를 통해 중복 승인·전송이 같은 작업을 두 번 시작하지 않도록 관리한다.
- 결과의 작업·계획 버전과 인계 조건을 확인한다. 완료 보고나 검증 통과만으로 무조건 다음 일을 시작하지 않는다.
- PM 자동 상태 변경은 명시적 재개 사이 12회로 제한한다. 발언·장부 기록은 세지 않는다([코드](../app/packages/core/src/action-limit.ts)).
- 범용 메신저·Agent 마켓플레이스·복잡한 조직 관리는 첫 MVP의 목적이 아니다. 대상 제품의 요구사항 충족을 계산하는 별도 모델도 현재 핵심 범위로 확대하지 않는다.

## 구현과 제품 의도 사이의 확인 사항

현재 `/`는 앱이 관리하는 프로젝트·worker 세션 중심이다. 개인 Agent의 비공개 작업과 명시적으로 공유한 팀 결과를 분리하는 제품 흐름, 외부 채널·IDE를 오가는 접근 권한과 맥락 연속성은 완성된 기능으로 주장하지 않는다. `/demo/design-to-code`는 이 의도를 설명하는 스크립트 시연이다.

`intent.md`의 **Team Work State**는 목표·작업·맥락·결정·산출물·변경 이력·담당·상태를 연결하는 제품 개념이다. 현재 이벤트 원장과 작업 모델은 일부를 표현하지만, 이 개념 전체가 구현됐다는 뜻은 아니다. 삭제한 대상 제품 요구사항 판정용 ProductState 설계와도 구분한다.

현재 [라우팅](../app/packages/core/src/routing.ts)은 가능한 Agent에게 우선 배정하고 사람 업무에는 판단·접근 권한·Agent 역량 부족 등의 사유를 요구한다. 이는 현재 구현 규칙이다. 사람이 실제 업무를 맡는 제품 의도를 “사람은 승인만 한다”로 줄이는 결정은 아니다. 실제 팀의 역할·가용 시간과 이 기본값이 맞는지 확인해야 한다.

[결정 기록](pm-agent-decisions.md)은 사용자 결정과 답변 전 채택한 기본값을 구분한다. 구현된 기본값을 새 제품 합의로 승격하지 않는다.

## 시연과 검증

- [런타임 시연](../app/demo/runtime/README.md): `/`의 자유형식·시나리오. 실제 서버·원장과 선택한 PM/Agent를 사용한다.
- [스크립트 시연](../app/demo/README.md): `/demo/pm-coordination`·`/demo/marketing-campaign`·`/demo/design-to-code`. 고정 대화·결과를 보여주며 실제 모델이나 외부 서비스를 실행하지 않는다.
- [현재 검사](qa/essential-regressions.md): 18개 핵심 회귀 검사. 모델 판단 품질이나 실제 팀의 수동 조율 감소를 측정하지 않는다.

남은 제품 검증은 실제 팀의 기존 흐름과 비교한 재설명·담당자 탐색·인계 재작업의 횟수와 시간, 필수 검토를 유지한 유효한 인계, 최신 결정·산출물 버전의 반영, 개인 작업·공유 범위의 통제다. 자동 시작이나 메시지 수만으로 성공을 판단하지 않는다. 목표치·참여 팀·반복 관찰 계획은 아직 확정하지 않았다.
