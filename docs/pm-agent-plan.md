## 2026-09-28 계획 원문

이번 MVP의 PM은 채널 하나에서 사람 2명과 실행 Agent 2명의 일을 잇는다. 목표와 가용 시간으로 계획을 제안하고, 결과물의 인계 조건을 살펴 다음 작업을 시작한다. 자연스러운 대화에서 필요한 순간에만 말하고, 결론을 계획과 관련 담당자에게 반영한다. 기한 예측은 코드가 계산하고 실행은 Codex 세션이 맡는다. 검증 승인 카드·`passed`·목표 달성 승인·`computeGap`, Claude Code 연결, 여러 채널, 정교한 복구·최적 배정은 이번에 만들지 않는다.

범위는 [MVP 범위](mvp-scope.md), 발언 판단은 [PM 원칙](pm-principles.md), 실행 전제는 [사용자 결정](pm-agent-decisions.md)을 따른다. [아키텍처](mvp-architecture.md)의 TypeScript·Next.js·SQLite와 패키지 의존 방향을 유지한다. 아래 경로는 별도 표기가 없으면 `app/packages/` 기준이며, 파일명·이벤트명은 추가할 설계다.

## 2. F4 상세: 듣기 → 판단 → 발언 또는 침묵

PM의 한마디는 팀의 주의를 쓴다. 행동을 바꾸는 말만 하고, 사람의 대화를 앞서 이끌지 않으며, 빠진 당사자에게 필요한 사실을 전하고, 결론이 흘러가지 않게 한다. 이 원칙을 PM 프롬프트의 기준으로 둔다.

| 순서 | 입력과 처리 | 남기는 것 |
|---|---|---|
| 듣기 | 메시지를 먼저 기록한다. LLM이 쟁점·제안·결론 후보와 근거 메시지를 추출한다. 후보를 곧바로 확정 지시로 바꾸지 않는다. | `message_recorded`, 관련 작업·열린 쟁점 |
| 사실 준비 | 코드가 원문과 기존 결정을 대조한다. 가용 시간 변경 후보의 기한 영향, 의존 작업, 대화 참여자, 변경을 확인한 사람, 위임 범위를 계산·조회한다. 미확정 입력의 계산은 조건부로 표시한다. | 입력 기록 ID·기준 계획 버전·계산값 |
| 판단 | LLM이 최근 대화와 계산된 사실을 보고 아래 세 질문에 짧게 답한다. 사람이 스스로 풀고 있는지도 판단한다. | `pm_considered`: 세 답, `speak` 또는 `silent`, 이유, 남은 쟁점 |
| 말하거나 기다리기 | `speak`이면 대상·행동·근거가 있는 한두 문장만 게시한다. `silent`이면 게시하지 않는다. | 발언은 `pm_spoke`로 판단 기록과 연결 |
| 다시 듣기 | 새 메시지·작업 결과·계획 변경 또는 대화가 멎은 시점에 미결 쟁점을 다시 살핀다. 기한에 영향이 있으면 다시 꺼낼지 판단한다. | 같은 근거로 이미 한 말은 반복하지 않음 |

대화가 멎었다는 신호는 재판단할 계기일 뿐 자동 발언 조건이 아니다. 특정 단어·고정 초 수·메시지 수로 개입을 결정하지 않는다. PM 자신의 게시를 새 사람 요청처럼 처리하지 않는다.

| 세 질문 | 코드가 제공할 사실 | LLM이 내놓을 답 |
|---|---|---|
| 이 말로 누구의 어떤 행동이 바뀌나? | 관련 작업·담당자, 선후 관계, 막힘, 현행/변경안의 기한 계산 | 대상과 다음 행동. 바뀔 행동이 없으면 침묵 |
| 그 사람이 이미 알고 있나? | 당사자 발언·명시적 확인·이전에 전달한 변경 ID | 알고 있음/확인 안 됨과 근거. 게시됐다는 이유만으로 읽었다고 가정하지 않음 |
| 근거가 기록이나 계산에 있나? | 원문·결정·첨부 ID, 계산 입력과 결과, 누락된 값 | 근거 ID 또는 필요한 질문. 근거 없는 주장을 하지 않음 |

세 답과 이유는 짧은 설명으로 남긴다. 모르는 값이 다음 행동을 막으면 그 누락 사실을 근거로 묻는다. 기록상 이미 알려진 내용은 되풀이하지 않고, 같은 변경 알림도 중복 발송하지 않는다.
예를 들어 휴가 발언 뒤 사람들이 조율 중이면 기록만 한다. “프로토타입이 밀리나?”에는 계산된 영향과 가능한 안을 말한다. “결제는 빼자”라는 결론은 위임 범위를 확인한 뒤 계획에 반영한다.

### “정리하면…” 확인·수정·권한 요청

| 상황 | 처리 |
|---|---|
| 명확한 합의이고 맡겨진 범위 안 | “정리하면: 초안 기준으로 계속, 결제 제외, 상세는 다음 주”처럼 결론·바뀐 일을 드러내고 vN+1로 반영한다. 매번 별도 승인 카드를 요구하지 않는다. |
| 결론이나 약속이 불명확 | 한 가지를 짚어 묻고 해당 변경은 보류한다. 침묵을 동의로 바꾸지 않는다. 사람의 가용 시간·새 약속은 그 사람의 답으로만 확정한다. |
| 맡겨진 범위 밖 | 원래 대화에서 권한 있는 사람에게 변경 내용·영향·필요한 권한을 묻는다. 답의 대상 변경과 기준 버전을 확인한 뒤 반영한다. PM은 자기 권한을 늘리지 않는다. |
| “아니, 그 뜻이 아니야” | 원문을 남기고 결론을 고친 새 계획 버전을 만든다. 관련자에게 수정 내용을 보내고 진행 중 Agent에도 다시 주입한다. 이미 한 작업을 없어진 것으로 표시하지 않는다. |

초기 계획에서 목표·기한·사람의 약속과 PM에게 맡길 범위를 명시한다. 추천은 그 범위 안의 순서·인계·계획 반영을 PM이 맡는 것이다. 위임 밖 목표·기한·범위 변경은 권한자에게 묻는다. 범위가 비어 있으면 이미 확인된 계획의 시작·인계만 자동으로 한다.
계획은 덮어쓰지 않고 이전 버전과 변경 이유를 남긴다. 한 번에 한 변경을 확정하며 기준 버전이 오래된 안은 다시 판단한다. 여러 조율을 자동 병합하지 않는다.
변경 대상은 코드가 담당·작업·입력 차이로 구한다. 사람에게는 자신에게 바뀐 일만 알리고, Agent에는 채널 알림과 별개로 직접 주입한다. 조율 스레드는 선택 사항이다.

## 3. F2 상세: Codex와 작업 기록 연결

`agents`의 연결 계약은 기동·작업 시작·변경 전송·출력 관찰·중지로 둔다. PM의 사내 proxy 호출은 기존 `llm`을 쓰고 Codex 계정 연결과 구분한다.
아래 메서드·알림 이름은 codex-cli 0.154.0의 `codex app-server generate-json-schema` 출력에서 확인했다(2026-09-28). 실제 설치 버전에서의 전체 왕복 확인은 M2에서 한다.

| 순서 | 연결과 앱의 처리 |
|---|---|
| 기동 | `codex app-server`와 표준 입출력 JSON-RPC로 연결한다. `initialize` 응답 후 `initialized`를 보내고 `thread/start`로 Agent별 세션을 만든다. 기존 연결은 `thread/resume`을 쓴다. |
| 작업 지시 | 기록에 시작 예약과 Agent 자리 점유를 함께 남긴 뒤 `turn/start`한다. 작업·계획 버전·입력 수정본·시작 요청 ID를 연결한다. 실제 턴 ID를 받아 실행 중으로 표시한다. |
| 진행 중 주입 | 업데이트 ID, 이전/새 버전, 유지·수정·폐기 대상과 이유를 저장한다. 현재 `threadId`와 `expectedTurnId`로 `turn/steer`한다. 수락은 `update_sent`이며 변경 이해를 뜻하지 않는다. |
| 확인 응답 | 앱이 요청한 `acknowledge_update` 형식의 JSON 보고에서 업데이트 ID·버전·수정/폐기 목록을 대조한다. 이는 앱의 출력 규약이며 Codex 기본 이벤트가 아니다. 일치할 때만 `update_acknowledged`를 남긴다. |
| 결과 회수 | `item/completed`의 보고와 `turn/completed`의 종료 상태를 모으고 필요하면 `thread/read(includeTurns: true)`로 대조한다. “완료” 문장이나 턴 종료만으로 인계하지 않는다. |
| 채널 게시 | 결과·첨부를 기록한 뒤 해당 Agent 이름과 원래 스레드에 한 번 게시한다. 내부 도구 로그 전체를 내보내지 않는다. PM은 결과 내용을 F3의 인계 조건과 대조한다. |

실행 Agent는 결과·첨부·질문·변경 확인만 제출한다. `orchestrator`가 형식·작업·버전을 검사해 원장에 쓴다. Agent에게 작업 기록 쓰기나 배정 변경 권한을 주지 않는다.
자료 확인→구성→작성→보고처럼 중간 산출이 있는 작업을 지시한다. [기존 실행 기록](pm-agent-decisions.md)에 따르면 변경은 단계 사이에서 반영되며, 먼저 만든 폐기 대상은 저절로 지워지지 않았다.
결과마다 작업·턴·계획 버전·입력 수정본·파일 목록을 받는다. 허용된 작업 폴더에서 회수한 사본을 고정하고, 변경 확인 뒤에도 폐기 항목이 남았는지 살핀다.
확인 전 결과, 버전이 불명확한 결과, 옛 계획 결과는 그렇게 표시해 보관하고 인계하지 않는다. 확인 응답 하나로 기존 파일 모두를 새 버전 결과로 취급하지 않는다.

| 경계 상황 | 최소 처리 |
|---|---|
| 같은 확인·보고가 다시 도착 | 시작은 작업·실행 회차, 확인은 업데이트 ID, 결과·게시는 턴·보고 ID로 중복을 막는다. 계획 번호만 바뀌었다고 시작 키를 새로 만들지 않는다. |
| 작업 종료와 주입이 겹침 | 활성 턴이 없어 steering이 실패하면 세션 상태를 조회한다. 끝난 결과는 옛 버전으로 보관하고, 수정이 필요할 때만 같은 작업의 다음 턴을 예약한다. |
| 전송 결과 불명확·연결 중단 | `thread/read`로 먼저 대조한다. 확인할 수 없으면 막힘을 표시하고 사람에게 알린다. 무조건 다시 시작하거나 계속 재전송하지 않는다. |
| 질문·승인 요청·잘못된 보고 | 필요한 사람에게 원래 작업과 연결해 묻는다. 세션의 도구 승인 요청도 답하거나 명시적으로 거절한다. 잘못된 출력은 상태를 바꾸지 않고 보완을 요청한다. |

Agent 자리는 턴 종료가 확인되어야 해제한다. 같은 Agent의 다음 지시는 대기시키고 다른 Agent는 병렬 실행할 수 있다. 재연결 고도화와 Claude Code 연결은 이후로 둔다.

## 4. M1~M4: 만들 것과 완료 기준

현재 `core`는 이벤트 봉투, `store`·`channel`·`scenarios`는 인터페이스 중심이다. `agents`는 역할 등록부, `orchestrator`는 빈 뼈대이며 `llm`에는 실제 호출 구현이 있다.

| M1 작업 순서 | 구체적으로 만들 것 | 단위 테스트에서 확인할 것 |
|---|---|---|
| 1. 기록·상태 | `core/src/events.ts`, `projection.ts`: 위 이벤트의 payload, 계획 버전·작업·사람·Agent·결과 투영. 기존 `LedgerEvent` 봉투를 재사용한다. | 같은 기록을 다시 읽으면 같은 상태. 기존 계획·결과는 새 기록으로만 대체 표시됨. |
| 2. 상태 전이 | `core/src/transitions.ts`: 대기→시작 예약→실행→결과 제출→인계 가능, 막힘·재개. 최초 계획 확인과 `checked`에서 준비된 작업을 찾는다. | 선행 조건 미충족·옛 버전 결과는 시작 불가. 독립 작업은 함께 준비됨. |
| 3. 저장·중복 방지 | `store/src/memory.ts`, `sqlite.ts`: `LedgerStore`에 현재 버전 검사와 시작 예약·Agent 점유를 한 트랜잭션으로 처리하는 계약 추가. 기록과 전달 예약도 함께 저장한다. | 같은 확인을 동시에 두 번 처리해도 같은 작업 시작 예약은 하나. 같은 Agent의 서로 다른 작업도 활성 예약은 하나. 메모리·SQLite 모두 확인. |
| 4. 기한 계산 | `core/src/forecast.ts`: §1 F5의 종료 범위·기한 차이·부족 시간·역할과 여유 시간별 후보 계산. | 주 10시간→5시간이면 같은 20시간 작업 예측이 늦어짐. 입력 누락은 날짜 없음. 0시간·순환 의존은 이유 표시. 한 사람의 시간 중복 없음. |
| 5. 권한·상한 | `core/src/authority.ts`, `action-limit.ts`: 위임 검사와 기록 기반 행동 횟수. 상한에서 자동 진행을 멈추고 한 번 알린다. | 위임 밖 계획 변경은 보류. 같은 사건 재처리는 횟수 중복 없음. 명시적 재개 없이 상한 우회 불가. |

M1에서는 LLM·Codex·웹 없이 입력 기록과 기대 상태로 검증한다. 테스트는 각 패키지의 `test/`에 두고 `app/`에서 `npm test`, `npm run typecheck`로 확인한다.

| 단계 | 만들 것 | 완료 기준 |
|---|---|---|
| M2 | `agents`의 실제 Codex 연결, 출력 보고 규약, `orchestrator`의 결과 기록·게시 연결 | 실제 세션 기동→작업→진행 중 “결제 제외” 주입→버전 확인→수정 결과·첨부 회수→게시 재현. 수락만 있고 확인이 없는 경우, 턴 종료와 주입이 겹치는 경우, 중복 출력·옛 결과의 인계 차단도 확인. |
| M3 | F3 인계와 맥락 전달, F4 판단·계획 변경·대상별 공유, 상한 연결 | 장면 2: 부족한 초안은 요청, 보완 뒤 프로토타입 시작 한 번. 장면 3: 휴가 대화 중 침묵, 필요한 기한 설명, 결론→v2→관련자 알림·주입→카드 데이터 갱신. 발언·침묵 모두 세 답과 근거가 기록됨. 질문→사람 답→원래 작업, 위임 밖 질문, 잘못 정리한 내용 수정도 재현. |
| M4 | F1 웹 채널·사용자 전환·첨부, F5 카드, F6 두 입력 모드 | 브라우저에서 아래 세 장면을 두 모드로 확인. 같은 기록의 화면·계획·카드가 일치하고 자유 입력도 대본 분기 없이 처리됨. `npm test`, `npm run typecheck`, `npm run build` 확인. |

1. 시작: “2주 안에 고객 반응 확인”에 가용 시간을 반영한 팀·계획 v1을 제안한다. 계획 확인 뒤 조사 Agent와 사람의 인터뷰가 병렬로 시작한다.
2. 인계: 디자이너가 흐름 초안을 첨부한다. 부족하면 보완을 요청하고, 보완되면 추가 시작 지시 없이 프로토타입 Agent가 초안으로 시작한다.
3. 조율: 제작 중 “목요일 휴가”, “결제는 빼자” 대화를 넣는다. 필요한 개입→결론 정리→v2→바뀐 사람 알림·Agent 변경 확인→수정 결과·로드맵 갱신까지 본다.

## 5. 큰 리스크와 대응

| 리스크 | 대응 |
|---|---|
| PM이 대화를 끊거나 필요한 말을 놓침 | 같은 상황에서 사람들이 아직 조율 중인 입력과 결론이 난 입력을 따로 관찰한다. 세 질문 답·실제 다음 행동을 대조해 프롬프트를 고친다. 단어별 개입 규칙을 늘리지 않는다. |
| 변경을 확인했지만 옛 결과가 남음 | 업데이트 확인과 산출물 내용을 따로 확인한다. 버전·폐기 목록이 맞지 않으면 인계하지 않고 수정 요청한다. |
| 시작·게시 중복 또는 전송 중단 | 원자적 예약·멱등 키·Agent 한 턴을 함께 지킨다. 불명확한 전송은 상태 조회 후 판단하고 자동 재기동하지 않는다. |
| 부정확한 가용 시간·작업 추정 | 최소~최대와 입력 근거를 표시한다. 모르면 질문하고 날짜를 숨긴다. 사람의 시간을 PM이 대신 약속하지 않는다. |
| Codex 계정·출력 규약 또는 PM proxy 응답 문제 | M2에서 실제 계정으로 왕복을 먼저 확인한다. 빈 응답·형식 오류는 상태를 바꾸지 않는다. 같은 proxy 요청 재시도로 해결된다고 가정하지 않고 자동 상한에서 사람에게 알린다. |

## 6. 사용자에게 확인할 질문

| 질문 | 추천안 |
|---|---|
| 검증 승인 카드·`passed`·목표 승인·`computeGap`을 이번에 제외해도 될까요? | 제외한다. “결과물을 본다”는 F3에서 실제 첨부와 인계 조건을 대조하는 것으로 지킨다. |
| 실행 Agent는 Codex부터 사용자 계정으로 연결하고, 사용할 모델·작업 폴더·허용 도구를 지정할까요? | Codex 계정과 지정 작업 폴더로 M2를 시작한다. 계정 사용 가능 여부·제한은 실제 연결로 확인한다. PM은 기존 proxy를 유지한다. |
| PM에 맡길 변경 범위와 “정리하면…”의 반영 방식을 어떻게 둘까요? | 초기 계획에서 맡긴 범위의 명확한 결론은 즉시 반영하고 수정은 새 버전으로 남긴다. 위임 밖 변경과 사람의 새 시간 약속은 해당 사람에게 묻는다. |
| 가용 시간·추정 입력 방식과 자동 행동 상한은 어떻게 둘까요? | 사람은 본인 주간 시간·작업 최소~최대를 입력하고 Agent 시간도 초기 값을 명시한다. 주간 시간은 7일 균등 환산한다. 자동 발언·계획 반영·작업 지시는 기록된 행동 단위로 총 12회 후 알리고 멈추는 값부터 추천한다. 알림 중복은 막고 명시적 재개 때만 횟수를 새로 센다. |
