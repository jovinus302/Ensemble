# AI PM 구현 계획

## 1. PM의 역할과 첫 범위

AI PM은 사람과 Agent가 함께 목표에 도달하도록 일을 잇는 팀원이다. 언제 끝나는지, 기한을 맞추려면 무엇이 얼마나 부족한지, 누가 가용하고 누구에게 맡길지 설명한다. 사람과 Agent 사이에 필요한 맥락을 전달하고 로드맵을 정리한다. 진행이 처음 계획과 달라지면 채팅에 스스로 참여해 쟁점을 모으고 당사자와 조율한다. 조율 내용을 결정과 새 계획으로 반영하고, 바뀐 담당·일정·입력·결과물 기준을 관련자 모두에게 공유한다.

기준은 [사용자 결정](pm-agent-decisions.md)과 이번 추가 결정이다. 실행 Agent는 Claude Code나 Codex 세션 자체를 런타임으로 쓴다. [제품 의도](../intent.md), [상태 모델](product-state-model.md), [Argo 규칙](argo-takeaways.md), [구현 구조](mvp-architecture.md)를 이어 적용한다. 미정인 권한 경계·수치·화면 구성은 아래 추천안으로 구분한다. 기존 문서는 수정하지 않는다.

| 확정된 기반 | 이번 계획에서 구체화할 것 |
|---|---|
| 자체 Slack형 앱, Next.js·TypeScript·SQLite, `app/` 모노레포 | 메인 채널 1개와 그 안의 조율 스레드 |
| 사람 2명, 실행 Agent 2개, PM 1개, 역할 틀 1종 | 사용자·디자이너·조사 Agent·프로토타입 Agent의 병렬 협업 |
| PM이 기본 결정자, 필요할 때 사람에게 권한 요청 | 위임받은 범위의 계획 변경은 PM이 승인. 사람의 시간 약속은 당사자가 결정 |
| 실제 LLM을 쓰는 시나리오·자유형식 모드 | 자동 인계와 조율 후 계획 변경·전달·작업 수정까지 시연 |
| 실행 Agent는 Claude Code·Codex 세션 사용 | PM은 앱에 두고 실행 세션과 원장을 연결한다 |

## 2. 채팅 속 조율 루프

| 단계 | 감지와 처리 | 사용자에게 보이는 것 |
|---|---|---|
| 감지 | 메시지·첨부·작업 사건에서 지연, 막힘, 가용 시간 변경, 상충하는 요구, 초안 교체, 결정 번복, 빠진 작업을 찾는다 | 필요할 때만 PM이 쟁점을 짧게 짚는다 |
| 후보 정리 | 읽기 전용 분류기가 발언 유형·근거 메시지·관련 작업을 추출한다. 잡담과 제안은 후보로 보관한다 | 확정 결정과 구분된 제안 표시 |
| 조율 시작 | 같은 쟁점은 기존 스레드에 묶는다. 영향받는 담당자에게 질문 하나와 선택지를 제시한다 | “초안을 먼저 넘기고 상세 설계는 병행할까요?” |
| 선택지 비교 | 현행 유지·단계 분할·순서 변경·담당 변경의 기한, 추가 노력, 재작업 영향을 계산한다 | 추천안, 이유, 아직 모르는 입력 |
| 결정 | 위임 범위이면 PM이 결정한다. 시간·업무 약속이 달라지는 사람에게 먼저 묻고, 위임 밖이면 권한자에게 요청한다 | 누가 무엇을 정했는지와 근거 |
| 계획 반영 | 결정·작업·의존성·담당·예상 종료·영향 산출물의 차이를 묶어 다음 계획 버전을 승인한다 | v1 → v2 변경 카드와 되돌리기 |
| 전달·추적 | 사람에게 변경 요약, Agent에게 구조화된 업데이트를 보낸다. 확인 응답과 적용 여부를 별도로 추적한다 | “디자이너 확인, 제작 Agent 전송됨·확인 대기” |

PM은 메인 채널에서 쟁점의 시작과 결론을 공유하고, 질문·대안·응답은 스레드에서 진행한다. 첫 버전에는 별도 방을 만들지 않는다. 스레드 밖에서 나온 관련 발언도 같은 쟁점에 연결한다.

### 채팅 참여 규칙

Agent는 채널의 팀 멤버이며 멤버 ID와 실행 세션 ID를 구분한다. PM은 멘션 없이 사건을 살피지만 실행 Agent는 아래 규칙으로 참여한다. 같은 Agent의 활성 턴은 하나로 제한하고 서로 다른 Agent는 병렬로 일할 수 있다.

| 들어온 메시지 | 참여 방식 |
|---|---|
| 사람의 Agent 멘션·Agent 답변에 대한 답글 | 참여 권한과 대상 작업을 확인한다. 설명 요청은 답변 턴으로, 새 업무는 PM의 계획·배정 경로로 보낸다 |
| 작업 중인 Agent를 향한 발언 | PM이 선별한다. 확정된 계획 변경·현재 작업에 필요한 정보는 같은 턴에 주입한다. 그 밖의 질문은 현재 턴이 끝난 뒤 답변 큐에서 처리하고 참고만 보관한다 |
| 단순 참조·공유 | 기록만 남기고 Agent를 실행하지 않는다. 별도 DM 기능은 첫 버전에 넣지 않는다 |
| Agent가 다른 Agent를 언급 | 인계 제안으로 받는다. 동료를 바로 깨우지 않고 PM이 조건과 권한을 확인해 배정한다 |
| 지시 권한이 없는 참여자의 요청 | 실행하지 않고 이유를 짧게 알린다. 위임 권한이나 세션 도구 권한을 넓혀 처리하지 않는다 |

Argo의 실행 중 메시지 대기 방식과 달리, 위 규칙의 중요한 변경은 현재 세션에 반영한다. 모든 발언을 무조건 주입하지 않는 것을 추천하며 §12에서 확인한다. 답변 본문의 멘션이나 끝부분 표식을 명령으로 해석하지 않는다.

합의 기록에는 문제, 선택한 안, 이유, 근거 발언, 당사자의 약속, 남은 이견, 변경 대상과 승인 주체를 넣는다. 사람 전원의 만장일치를 요구하지 않는다. PM 권한 안의 작업 방식은 PM이 정하되, 남의 시간 약속을 침묵으로 대신 확정하지 않는다.

PM이 물은 질문에 대한 답은 질문 ID·대상·계획 버전·응답 권한을 확인한다. 현재 제안에 명확히 답한 경우 추가 확인 카드를 만들지 않는다. “좋아요”가 어느 안을 뜻하는지 불명확하거나 안이 바뀌었으면 다시 묻는다. 자발적인 결정성 발언은 후보로 받아 PM이 권한 범위에서 별도 결정을 내리거나 확인을 요청한다.

| 순차적이지 않은 진행 | 처리 |
|---|---|
| 초안부터 인계 | 초안 제출을 별도 작업으로 나누고 인계 조건을 정한다. 초안 작업이 `checked`가 되면 제작을 시작하고 상세 설계는 계속한다 |
| 병렬 작업 | 선행 조건을 만족하고 인원·실행 자리가 있으면 함께 진행한다. 순번을 강제로 만들지 않는다 |
| 입력 초안이 바뀜 | 소비한 산출물 수정본을 추적한다. 관련 제작 작업만 영향 표시하고 변경 부분을 전달한다 |
| 되돌아감 | 이전 결과를 삭제하지 않는다. 수정 작업과 새 산출물 수정본을 만들고 후속 작업의 계속·수정·취소를 결정한다 |
| 새 결정이 이전 결정을 대체 | 연결된 조건·작업·증거의 영향을 계산하고 새 계획에 포함한다. 관계가 불명확하면 해당 부분의 인계를 보류하고 묻는다 |

## 3. PM의 결정 권한

시작할 때 목표·완료 조건·고정 기한·참여자·가용 시간·비용 한도·PM 위임 범위를 한 카드로 확인한다. 최초 계획도 이 카드에 묶는다. 이후에는 위임받은 조건 안에서 PM이 계획을 승인한다. 위임 항목이 비어 있으면 기존 승인 계획의 인계·수정 요청만 자동으로 진행한다.

| PM이 혼자 정함 | 당사자에게 물음 | 사람의 승인을 받음 |
|---|---|---|
| 승인 계획의 시작·인계·수정 요청·정보 도착 후 재개 | 불명확한 요구·첨부의 의미·작업량 추정 | 목표, 완료 조건, 고정 기한의 변경 |
| 목표와 완료 조건을 유지하는 작업 추가·분할·순서 조정 | 초안으로 먼저 일할 때 필요한 입력과 재작업 부담 | 제공하기로 한 동작 삭제·새 동작 약속 등 위임 밖 범위 변경 |
| 같은 역할 틀 안에서 권한·가용 자리를 확인한 Agent 배정 변경 | 사람의 새 업무 약속·담당 변경·합의된 시간 초과 | 새 역할·팀원 도입, 비용 한도 확대, 외부 공개, 되돌리기 어려운 행동 |
| 합의된 사람의 업무·시간 한도 안에서 세부 순서 조정 | 사람의 가용 시간 갱신. 거절하면 다른 안 계산 | 위임 정책 변경·자동 진행 상한 도달 후 재개 |
| 인계에 충분한지 판단하는 `checked`, 위임 안의 결정·계획 변경 | 충돌하는 의견의 사실관계와 이해관계 | 검증 카드 승인, 최종 목표 달성 승인 |

권한 검사는 코드가 한다. 주체·행위·대상·위임 정책 버전·시간과 비용 한도를 확인한다. PM은 자기 권한을 늘릴 수 없다. 실행 Agent가 Ensemble에 제출할 수 있는 것은 결과·첨부·질문·업데이트 확인이다. 세션의 파일 작업 권한은 별도로 제한하고 원장·배정·검증 상태를 직접 바꾸게 하지 않는다.

| 기존 문서와의 충돌 | 제안과 이유 |
|---|---|
| 상태 모델 §0: 계획 밖 작업·담당 교체·영향 처리는 사람 확인 | 위임 안이면 PM이 계획 v+1을 먼저 승인한 뒤 실행한다. `within_plan`은 유지하고 계획 승인 주체를 확장한다. 미승인 계획 밖 실행은 허용하지 않는다 |
| intent §7: 범위·외부 공개·비용·불가역 행동, 사람 일정 | 작업 방법·분할은 PM에 위임한다. 약속한 결과를 바꾸거나 바깥에 영향을 주면 사람 승인을 받는다. 승인된 모델 사용 예산 안의 호출은 반복 승인하지 않는다. 사람 일정 자율성은 유지한다 |
| intent §9: 사람 결과 후 자동 인계 한 장면 | 그 장면을 유지하고, 진행 중 조율 → 새 계획 → 전달 확인 → 수정된 결과까지 첫 시연에 포함한다. 사용자가 추가로 요구한 가치를 함께 확인한다 |
| intent §9: 채널 하나 | 메인 채널 안의 스레드를 쓴다. 별도 방도 허용된 선택이지만 첫 버전에 다중 채널 관리가 필요하지 않다 |
| 상태 모델 §7: 변경 영향 처리는 이후 단계 | 연결된 결정·조건·산출물의 영향 표시, 옛 증거 무효화, 실행 중 업데이트, 취소·수정을 이번에 넣는다. 다중 프로젝트 영향과 CI 연동은 뒤로 둔다 |
| 상태 모델 결정 2: `passed`는 증거 또는 사람 승인 | 유지한다. PM 운영 승인과 검증은 다르다. PM·Agent의 자신감만으로 `passed`가 되지 않는다. 첫 시연의 검증은 지정한 사람의 카드 승인을 쓴다 |

Argo의 “규칙 변경은 결정권자만”도 위임받은 PM의 계획·결정 변경을 허용하도록 좁혀 해석한다. 위임 자체와 목표 승인 권한은 사람에게 남긴다. `goal` 달성은 모든 채택된 조건의 충족과 사람의 명시적 승인 둘 다 있어야 한다.

## 4. 진행 중 Agent에 업데이트 전달

Claude Code·Codex 세션이 작업 중 받은 메시지를 다음 단계에 반영하는 steering을 이미 제공한다는 사용자 확인을 전제로 한다. 앱이 자체 Agent 도구 루프를 다시 만들 필요는 없다. 이 방식도 단계 사이에 반영된다는 한계가 있으며, 실제 연결에서 반영 시점을 어떻게 관찰할지는 따로 확인한다.

§2.3에서 확인한 흐름은 첫 도구 결과 뒤 PM 업데이트 전달 → `acknowledge_update` → 온보딩 수정이었다. 먼저 병렬 생성한 결제 섹션은 남았다. 따라서 세션이 메시지를 받았다는 사실, Agent의 변경 확인, 실제 결과 반영을 따로 추적한다.

| 책임 | 설계 |
|---|---|
| Claude Code·Codex 세션 | 대화 맥락, 작업 단계 실행, 기본 파일·도구 작업, 진행 중 입력의 다음 단계 반영 |
| 앱의 PM | 조율·권한·계획·배정, 전달할 맥락, 변경 영향과 결과의 인계 가능 여부 |
| 앱의 세션 연결부 | 작업과 세션 ID 연결, 기동·재연결, 업데이트 전달, 진행·질문·결과 수집, 중복·옛 응답 구분 |

세션 재사용으로 steering·파일 작업·도구 루프 구현을 줄일 수 있다. 이 PC에서 2026-09-28에 CLI 도움말과 app-server 프로토콜 스키마로 확인한 연결 방식은 다음과 같다. 모델·계정·비용·도구 권한의 운영 조건은 §12에 남긴다.

| 확인된 실행 환경 | 기동·입력·회수 연결 |
|---|---|
| Claude Code 2.1.283 | `claude -p --input-format stream-json --output-format stream-json`으로 기동. 같은 프로세스에 스트리밍 입력을 보내고 스트림 출력에서 진행·질문·확인·최종 보고를 수집한다 |
| codex-cli 0.154.0 | `codex app-server`의 JSON-RPC 사용. `thread/start`·`thread/resume`으로 세션 연결, `turn/start`로 작업 시작, 실행 중에는 `turn/steer`, 중지는 `turn/interrupt`. `thread/read`로 세션 기록을 회수·대조한다 |
| Orca terminal send | 새 턴 시작 감지만 확인됐다. mid-turn 전달 여부를 이 신호로 판정하지 않고 실행 세션의 변경 확인 응답을 받는다 |

MVP는 작업 중 입력 경로가 명시된 Codex app-server 연결부터 구현하도록 추천한다. 두 실행 역할을 서로 다른 세션으로 운영한다. Claude Code용 연결부는 같은 앱 내부 계약에 stream-json 입출력을 매핑하는 두 번째 선택지다. 두 공급자 동시 지원을 첫 완료 조건으로 늘리지 않는다.

| 세션 수명과 steering | 앱이 지켜야 할 동작 |
|---|---|
| 기동·유지 | 프로젝트·채널·Agent별 세션 연결을 찾아 이어 쓰고 없을 때만 기동한다. 턴마다 작업·계획 버전·실행 세대를 연결한다. Codex는 `thread/resume`으로 이어가며, 같은 Agent에 다른 턴을 겹쳐 시작하지 않는다 |
| 작업 전달 | 목표·현재 조건·입력 수정본과 함께 자료 확인 → 구성 → 섹션 작성 → 조립 → 보고의 짧은 중간 결과를 요청한다. 내부 도구 호출 순서를 앱이 직접 운전하지 않는다 |
| 변경 전달 | 업데이트 ID, 이전·새 계획 버전, 유지·수정·폐기 대상과 이유를 저장한다. Codex는 현재 턴에 `turn/steer`, Claude Code는 같은 프로세스의 스트리밍 입력으로 보낸다. 아직 반영 전이면 “다음 단계에 적용”으로 표시한다 |
| 확인 응답 | 세션 출력으로 `acknowledge_update`에 해당하는 구조화된 응답을 요청·회수한다. 최신 업데이트 ID·버전·수정 및 폐기 목록을 검사한다. JSON-RPC 수락 응답·입력 쓰기 성공·Orca의 새 턴 감지는 Agent의 확인을 대신하지 않는다 |
| 결과 회수 | Claude Code는 스트림 출력, Codex는 프로토콜 출력과 `thread/read` 기록에서 결과 보고를 수집한다. 산출물 목록에 파일 위치·수정본·해시·작업·계획 버전을 묶는다. 종료 코드나 “끝났다”는 문장만으로 완료 처리하지 않는다 |
| 채널 게시 | 연결부가 최종 답변을 해당 Agent 이름과 원래 스레드로 게시한다. 첨부는 허용된 작업 폴더 안의 보고된 파일만 회수한다. 내부 추론과 도구 스트림 전체를 채널에 내보내지 않는다 |
| 결과 확인 | 확인 응답 뒤에도 변경된 조건 충족과 폐기 섹션 제외를 대조한다. 확인 전 결과나 옛 버전 결과는 기록만 하고 인계하지 않는다 |
| 연결 중단 | 마지막 수신 위치와 미전달 업데이트를 저장한다. 기존 세션의 생존·상태부터 확인해 재연결하며, 전송 결과가 불명확한 업데이트는 ID로 중복을 구분한다 |
| 무응답·실패 | 합의한 단계 제한 시간에 진행·확인이 없으면 상태를 조회한다. 재요청 후에도 확인할 수 없으면 `blocked`. 끝 보고 없는 중단은 사람 재개 전 담당을 바꾸지 않는다 |

앱 내부 연결 계약은 `start`, `sendUpdate`, `observe`, `resume`, `stop`으로 나누고 위 실제 프로토콜에 연결한다. Codex의 `turn/steer`는 현재 턴 ID를 검사하며 활성 턴이 없으면 실패한다. 이때 같은 스레드의 상태를 읽고, 작업이 아직 필요하면 최신 계획으로 다음 턴을 시작한다. 근거: `codex app-server generate-json-schema`의 `TurnSteerParams`(필수 `threadId`·`input`·`expectedTurnId`, 활성 턴과 다르면 실패). 선택 필드 `clientUserMessageId`에 업데이트 ID를 실어 중복 전달을 구분한다.

앱은 업데이트 ID를 가진 확인 응답과 결과 보고 형식을 세션에 요청한다. 이를 CLI 자체의 기본 이벤트라고 가정하지 않는다. 확인 응답이 없으면 전달됨 표시를 확정하지 않는다. 프로토콜에서 요청을 수락한 상태와 Agent가 변경을 이해한 상태를 분리한다.

두 런타임에는 결과 보고·질문·변경 확인에 같은 앱 도구 규격을 제공한다. 실제 연결은 세션별 도구 연결 방식에 맞추며 원장 쓰기 권한은 주지 않는다. 최종 답변 게시와 업무 상태 변경은 구분한다. Argo의 답변 게시 방식은 참고하되, 문장 끝 제어 표식은 옮기지 않고 구조화된 보고와 원장 사건으로 처리한다.

긴 맥락은 명령줄 인자에 넣지 않고 stdin·프로토콜 메시지로 전달한다. 세션이 앱에 보내는 승인·도구 요청은 모두 처리하거나 명시적으로 거절한다. 모르는 요청을 방치해 턴이 멈추지 않게 한다. 세션의 사람 승인이 필요한 요청도 채널 카드와 연결한다.

업데이트는 같은 세션으로 보내고 매번 종료·재기동하지 않는다. 작업 단계·진행 알림의 제공 방식은 세션별로 확인한다. 앱이 세션 내부 모든 도구 실행을 중간에 막을 수 있다고 가정하지 않는다. 즉각 중지가 필요한 위험은 세션 권한으로 사전에 제한하고, 중지 요청을 보내도 이미 발생한 효과를 되돌렸다고 표시하지 않는다.

작업 폴더는 세션별로 분리하고 앱이 회수한 산출물 사본은 실행 세대별로 보관한다. 계획 변경 전에 시작된 병렬 도구가 늦게 파일을 써도 새 기준의 결과로 바로 채택하지 않는다. 보고된 파일과 회수한 내용의 해시가 다르면 다시 회수한다. 확인된 사본을 고정해 미확인 결과가 현재 산출물을 덮어쓰지 못하게 한다.

산출물에는 작업·세션·실행 세대·계획 버전·조건 버전·입력 수정본을 묶는다. 확인 응답이 왔다고 같은 세션의 모든 후속 파일을 새 버전으로 간주하지 않는다. 산출물별 적용 버전을 식별할 수 있는지 M2에서 확인하고, 불명확하면 인계를 보류한다. 무효 섹션은 원본을 보존해 “이전 계획의 결과”로 표시하고 조립·인계에서 제외한다. 세션의 자체 테스트 결과도 claim이며 신뢰된 검증 증거로 자동 승격하지 않는다.

계획 번호만 바뀌고 참조 조건·입력이 같은 결과는 영향 없음 확인 후 재사용 관계를 기록한다. 업데이트가 여러 개면 이력을 보존한 최신 묶음을 전달하고 최신 버전을 확인받는다. 확인된 프로토콜을 앱에 연결해 기동·주입·결과 회수를 재현하는 작업을 M2의 첫 완료 항목으로 둔다.

대안인 앱 직접 API 도구 루프는 이번에 구현하지 않는다. 직접 제어하기 쉽지만 세션이 제공하는 steering·파일·도구 실행을 다시 만들어야 하므로, 세션 연결 제약이 확인될 때만 재검토한다.

## 5. 기한·부족분·가용 인원·배정

| 필요한 입력 | 입력 주체와 빠졌을 때의 처리 |
|---|---|
| 목표 기한·시간대·고정 여부·우선순위 | 사용자가 시작 카드에 입력한다. 없으면 기한 여유와 지연을 “미정”으로 표시한다 |
| 역할·가능한 업무·날짜별 가용 시간·기존 약속 | 사람이 자기 값을 입력·수정한다. 미입력은 무제한도 0시간도 아닌 “확인 필요”다 |
| 작업별 남은 노력의 최소·최대, 의존성, 외부 대기 | 사람은 본인 작업을 추정하고 Agent 작업은 단계 수·실측 시간을 쓴다. PM 추정은 근거와 함께 임시로 표시한다 |
| Agent 역량·동시 세션 자리·사용 예산 | 역할 틀과 확인된 실행 설정에서 읽는다. 실측이 없으면 날짜를 확약하지 않고 조건부 범위로 제시한다 |
| 인수 조건·담당 작업·증거·산출물 최신 버전 | 원장에서 읽는다. 자료가 없으면 충족으로 보지 않고 구체적으로 요청한다 |

| 코드가 계산할 것 | LLM이 도울 것 |
|---|---|
| 충족하지 못한 조건, 열린 작업으로 덮이지 않은 `computeGap` | 빠진 일을 해결할 작업 초안과 누락 이유 |
| 휴일·가용 시간·이미 예약한 시간, Agent 자리의 중복 배정 방지 | 작업에 필요한 역량 해석과 담당 후보의 장단점 |
| 의존성 순환 검사, 준비된 작업을 빈 시간에 배치한 예상 종료 범위 | 작업 분할, 초안 선행, 병렬화와 재작업 위험 설명 |
| 최소·최대 노력 각각의 일정, 최종 작업과 검증 대기의 종료 시점 | 추정 근거가 약한 곳 식별과 당사자에게 할 질문 |
| 기한 대비 지연, 역할별 추가 시간, 후보 배정별 재계산 | 시간 추가·범위 조정·기한 변경 중 추천안과 이유 |

첫 계산기는 위임된 우선순위, 기한, 작업 ID 순으로 준비된 작업을 배치한다. 인원 한 명의 같은 시간을 두 작업에 겹쳐 쓰지 않는다. Agent 대기열도 반영한다. 최적 일정이라고 주장하지 않는다.

예상 시작은 선행 인계·결정 해결·담당자의 다음 빈 시간 중 가장 늦은 시점이다. 그 뒤 가용 시간에 남은 노력을 채워 종료를 계산한다. 날짜 차이는 달력 기준 지연, 부족 노력은 역할별 시간으로 따로 표시한다. 외부 답변 시점이 없으면 “답변 후 2~3일”처럼 조건부로 표시한다.

역할별 부족 시간은 기한까지 필요한 노력에서 실제 배치 가능한 시간을 뺀 값이다. 같은 역할의 남는 시간도 역량과 선행 조건이 맞을 때만 쓴다. “디자인 8시간 부족”을 곧바로 “사람 1명 추가”로 바꾸지 않는다. 후보가 그 구간에 참여했을 때 종료가 앞당겨지는지 다시 계산한다. 병렬화할 수 없으면 인원 추가로 기한을 맞출 수 없다고 설명한다.

`computeGap`은 미검증 조건 전체와 다르다. 열린 작업이 맡은 조건은 gap에서 빠져도 아직 충족되지 않았을 수 있다. 로드맵에는 미충족 조건, 담당 없는 조건, 검증 대기를 따로 보인다. gap이 비었다는 이유만으로 목표 승인 카드를 보내지 않는다.

## 6. 사람과 Agent 사이의 맥락 연결

| 방향 | 전달할 것 | 넘기지 않을 것 |
|---|---|---|
| 사람 → Agent | 목표 요약·역할, 확정 결정과 이유·제약·제외 범위, 작업의 인수·인계 조건, 선행 산출물 위치·수정본, 이번 첨부, 관련 최근 대화 | 전체 원장, 무관한 대화, 미확정 후보를 확정 지시처럼 표현한 내용 |
| Agent → 사람 | 결과물 위치·기준 버전, 달라진 점, 근거와 한계, 막힌 이유, 사람에게 필요한 판단·다음 행동 | 내부 사고 과정, 장황한 도구 로그, 근거 없는 완료 확언 |
| 사람 → 사람 | 쟁점·이미 합의한 내용, 역할별 영향, 시간 약속, 필요한 입력, 결정 이유와 원문 링크 | 상대의 가용 시간을 추측한 약속, 관련 없는 개인 자료 |

맥락의 칸을 고정하고 각 칸에 출처를 붙인다. 프로젝트·채널·발언자와 권한, 답글의 부모 메시지, 다른 담당자의 현재 작업도 넣어 중복 작업을 줄인다. 열린 질문은 “아직 모름”으로 구분한다. 토큰이 부족하면 최근 대화부터 줄이고 제약·현재 조건·변경 사항을 남긴다. 관련 없는 개인 메모·원시 오류·비밀은 넘기지 않는다. 중요한 자료를 생략했으면 링크와 생략 사실을 표시한다.

초안 전달에는 사용 가능한 부분, 아직 바뀔 부분, 소비한 수정본을 적는다. 사람이 재전달하지 않아도 원본이 바뀌면 PM이 영향을 받은 담당자에게 차이를 전한다. 실행 Agent끼리 직접 배정하거나 서로를 호출하는 경로는 만들지 않는다.

## 7. 로드맵과 상황 공유

| 시점 | 위치 | 내용 |
|---|---|---|
| 시작·계획 변경 확정 | 메인 채널의 변경 카드, 고정 로드맵 | 목표·기한, 단계별 담당·예상 종료 범위, 병렬 작업, 변경 이유·전후 차이 |
| 인계·막힘·검증·업데이트 상태 변화 | 같은 로드맵 카드와 상태 패널 갱신 | 현재 작업, 막힌 이유·풀 사람, 미충족 조건, 다음 행동, Agent 적용 대기 |
| 당사자 답변 필요 | 해당 조율 스레드, 당사자 알림 | 답할 질문 하나, 선택지, 답이 없을 때 영향 |
| 기한 위험·조율 결론 | 메인 채널에 짧은 요약 | 부족한 역할·시간, 선택한 대책, 영향받은 사람·Agent, 상세 스레드 링크 |

관련자 모두는 메인 채널과 로드맵에서 같은 확정본을 본다. 행동이 달라진 당사자에게만 알림과 확인 요청을 보낸다. 전송됨·세션이 확인함·결과에 반영됨은 서로 다른 상태로 보인다.

사건이 연속되면 5초 동안 묶어 카드 한 장을 갱신한다. 같은 쟁점의 미응답 질문은 덧붙여 새로 보내지 않는다. 일반 요약은 마지막 게시 후 10분 안에는 새 메시지를 만들지 않고 카드만 갱신한다. 직접 질문에 대한 답, 막힘과 권한 요청은 즉시 보낸다. 숫자는 조정 가능한 초기값이다.

상황 정리는 사건이 생기거나 사람이 요청할 때 실행한다. 정해진 시각에 Agent를 반복 실행하는 예약 기능은 넣지 않는다. 타임아웃 점검은 실행 복구용이며 새 업무를 만드는 계기가 아니다.

## 8. 원장·계획 버전·모듈

현재 `core`는 사건 봉투, `store`·`channel`·`scenarios`는 인터페이스 중심이다. `agents`에는 역할 등록부가 있고 `orchestrator`는 비어 있다. `llm`만 실제 proxy 호출이 구현되어 있다. 아래는 이 뼈대에 추가할 책임이다.

| 원장 사건 묶음 | 저장할 핵심 내용 |
|---|---|
| `decision_proposed/confirmed/superseded`, `open_item_opened/resolved` | 근거 메시지·질문·선택지, 이유, 권한 주체, 영향 조건 |
| `coordination_opened/resolved`, `commitment_confirmed` | 스레드·관련자·쟁점, 선택한 안, 당사자가 약속한 업무·시간 |
| `authority_granted`, `availability_updated`, `estimate_updated` | 위임 범위·버전·기간, 사람별 가용 시간, 작업량과 추정 출처 |
| `plan_proposed/approved/superseded` | 이전 버전, 전체 계획 스냅샷과 차이, 승인 주체·위임 근거, 변경 이유 |
| `task_started/blocked/resumed/checked/impacted/cancelled` | 실행 세대, 선행 조건, 인계 판단 사유, 원인 사건 |
| `claim_recorded`, `artifact_recorded/superseded` | 작업·조건·계획 버전, 입력 수정본, 결과 위치·대체 관계 |
| `evidence_recorded/invalidated`, `goal_approved` | 증거 출처·생산자·승인자, 조건 버전, 최종 목표 승인 주체 |
| `update_queued/sent/acknowledged/applied` | 대상 작업, 업데이트 ID·버전, 확인 내용·결과 참조 |
| `session_linked`, `turn_observed`, `reply_recorded` | Agent 멤버·세션·턴·작업 연결, 입력 메시지·수신 위치, 채널 답변과 첨부의 중복 방지 키 |
| `action_limit_reached`, `execution_failed`, `progress_published` | 누적 행동 수·실패 사유, 재개 권한, 공유 카드 ID·근거 원장 위치 |

공통으로 프로젝트·대상 제품·주체·원인 사건·근거 메시지·멱등 키를 남긴다. 원장은 덧붙이기만 한다. 자유 발언 후보는 `ps_intake`에 보관하고 확정된 제품 상태와 분리한다. PM이 발행한 결정·요약은 같은 원인 사건을 다시 처리하지 않아 자기 메시지로 조율을 반복하지 않는다.

| 위치 (`app/packages/` 아래) | 책임 |
|---|---|
| `core/src/` | 기존 상태·증거·gap 규칙, 계획 차이와 영향 계산, 권한 검사, 일정·자원 계산, 순수 상태 전이 |
| `store/src/` | SQLite·메모리 저장소, 원장과 투영의 원자적 저장, 계획 동시 갱신 검사, 실행권·전달 대기열 저장 |
| `orchestrator/src/` | 발언 분류, 조율, 계획 작성·승인 요청, 인계 판단·배정, 맥락 구성, 로드맵 갱신 |
| `agents/src/` | 역할 등록·같은 앱 도구 규격·세션 연결 계약, 런타임별 입출력 변환, 기동·재연결·결과 회수. 세션의 구조화된 출력을 orchestrator에 전달 |
| `llm/src/` | PM의 분류·계획·인계 판단용 기존 Anthropic 호출, 응답·사용량·재시도 기록. 실행 Agent의 내부 모델 루프는 다루지 않음 |
| `channel/src/` | 멤버·스레드·첨부·카드, 대상 버전·질문 ID·카드 갱신 계약, 원장 사건을 표시하는 어댑터 |
| `scenarios/src/` | 사람 발언·첨부 재생, 대상 작업·버전까지 지정하는 사건 대기 조건, 관찰값 수집 |

`app/apps/web`은 채널·스레드·상태 패널·가용 시간 입력·버전 차이를 보여 주고 서버 경로로만 쓴다. 저장소는 SQLite이므로 상태 모델의 PostgreSQL RLS 문법을 옮기지 않고 같은 접근 제한을 서버 서비스에서 검사한다. 의존 방향은 기존 아키텍처를 유지한다.

계획 v+1은 이전 승인 버전을 참조하며 승인 뒤 수정하지 않는다. 결정 변경·조건 버전·증거 무효화·영향 작업·계획 승인을 한 트랜잭션으로 저장한다. 두 조율이 같은 버전에서 출발하면 먼저 승인된 변경을 반영해 뒤 안을 다시 계산한다. 승인 대상 내용이 달라졌으면 기존 사람 답변을 재사용하지 않는다.

`LedgerStore.append`에는 기대 계획 버전 검사와 실행권 획득을 같은 트랜잭션에서 처리할 계약이 필요하다. 작업 ID·실행 세대·상태 전이로 실행권을 유일하게 만든다. Agent별 활성 턴 점유권도 함께 얻어 설명 답변과 업무 턴이 겹치지 않게 한다. 실행권 예약만으로 `running`을 표시하지 않고 실제 작업 시작 뒤 `task_started`를 기록한다. 계획 번호만 바뀌었다고 영향 없는 작업을 다시 시작하지 않는다.

원장 저장과 전달 대기열 적재는 함께 완료한다. 저장 후 전송 전에 서버가 꺼져도 재시작 시 미전달 항목을 보낸다. 같은 전달이 재시도돼도 실행권·카드·확인 응답은 한 번만 적용한다. 외부 세션 기동·메시지 수락의 단 한 번 실행까지 보장하지는 않는다. 전송 결과가 불명확하면 세션 상태를 확인하고 늦은 응답과 중복 결과를 원장에서 차단한다.

입출력은 수신 위치를 저장하고 중복 전달을 전제로 처리한다. 대화 답변은 Agent·원본 메시지·답변 종류로, 업무 시작은 작업 상태 전이로 중복을 막는다. 최종 답변 저장·관련 보고 처리·게시 대기열 적재를 한 트랜잭션으로 묶고 재전송에도 채널 답변을 한 번만 표시한다. 대기 중 계획이 바뀌거나 요청 기한이 지나면 재검사하고 실행할 수 없는 이유를 알린다.

확정 사건의 후속은 하나의 처리로 묶는다. 계획 승인은 준비된 작업 배정, 결정 확정은 관련 대기 해제, `checked`는 후속 작업 준비 검사, 검증 승인은 상태 계산만 수행한다. 여러 작업이 준비되면 각 작업의 실행권을 따로 얻는다. 검증 승인이 두 번째 시작을 만들지 않는다.

되돌리기는 과거 기록 삭제가 아니라 보완 사건과 새 계획 버전이다. 이미 진행한 작업·비용은 사라지지 않는다. 끝 보고 없이 멈춘 실행은 `blocked`로 두고, 사람이 재개하기 전에는 담당자를 바꾸지 않는다. 정보 대기 작업은 해당 정보가 기록되면 자동 재개한다.

## 9. M1~M4 구현 순서와 완료 기준

| 단계 | 만들 것 | 테스트나 시연에서 확인할 것 |
|---|---|---|
| M1: 상태와 계산 | 원장·투영·저장소, 계획·위임·작업·조건 버전, 가용 시간·일정·gap 계산 | 완료 보고로 검증 상태가 바뀌지 않음. 미검증과 담당 없는 조건 구분. 시간 미입력·중복 배정·의존 순환 처리. 동시 계획 승인 한쪽만 반영. 옛 증거 재사용 차단 |
| M2: PM과 실행 세션 | 세션 기동·작업 중 주입·결과 회수, 공통 도구 규격. 역할 틀·맥락·조율·계획·인계·상한·복구 | 같은 세션에서 업데이트 확인과 결제 제외. 초안 후 병렬 작업. 같은 Agent에 활성 턴 하나. 재시작·중복 입력에 중복 기동·게시 없음. 옛 결과 격리, 권한·참조 구분, 서버 요청에 응답 |
| M3: 채널에서 운영 | 스레드·첨부·승인 카드·로드맵·가용 시간 입력, 분류·직접 답변 처리, 사람 2명 전환 | 원장과 화면 일치. PM 자동 참여. 당사자 시간 거절 반영. 오래된 승인 카드 거절. 계획 변경을 사람·Agent 모두 확인. 같은 쟁점 알림 중복 없음 |
| M4: 두 모드 시연 | 아래 장면, 같은 엔진의 자유 입력, 실행·인계·개입 지표 | 전체 장면에서 재지시 없이 작업 연결. 조율 뒤 새 계획과 산출물 내용 일치. 미검증을 완료로 표시하지 않음. 실패·상한에서는 명확한 사유와 재개 경로 표시 |

M1~M3는 관련 동작 테스트와 `app/`의 `npm test`, `npm run typecheck`를 완료한다. M3~M4는 `npm run build`도 확인한다. M2는 PM proxy의 `npm run smoke:llm`과 별도로 실행 세션 연결·steering·결과 회수를 확인한다. 정해진 응답을 쓰는 테스트는 재현성을 위해 사용하고, 시연의 PM·Agent 답변을 대신하지 않는다.

## 10. 시나리오 모드와 자유형식 모드

시나리오 모드는 사람 발언과 첨부만 준비한다. PM은 실제 API를, Agent는 실제 Claude Code·Codex 세션을 쓴다. 사람 입력 시점은 고정 지연 대신 해당 작업·계획 버전의 원장 사건에 맞춘다. 자유형식 모드도 같은 분류·조율·배정·세션 연결부를 쓴다.

| 장면 | 관찰할 행동 |
|---|---|
| 목표와 시작 | “2주 안에 고객 반응 확인”. 사용자와 디자이너의 가용 시간·위임 범위를 확인하고 계획 v1 시작. 조사와 인터뷰 병렬 진행 |
| 사람 결과로 인계 | PM이 고객 문제 선택을 질문하고 사용자 답을 기록. 디자이너가 부족한 초안을 올리면 구체적 보완 요청. 보완 후 누구도 “시작해”라고 말하지 않아도 제작 Agent 시작 |
| 초안 이후 조율 | 제작이 진행되는 동안 디자이너가 시간 부족과 결제 흐름 제외·관심 분야 추가를 제안. PM이 스레드를 열고 일정·영향 비교. 제품 동작 변경 승인은 사용자에게 한 번 받고 디자이너의 시간 약속을 확인 |
| 새 계획으로 이어가기 | PM이 v2를 반영·공유. 제작 Agent는 다음 단계에서 업데이트를 확인하고 수정. 디자이너의 상세 설계와 제작은 병행. 이전 결제 결과는 최종 묶음에서 제외 |
| 되돌아감 | 초안 수정본이 다시 올라오면 소비한 제작 부분만 영향 표시. PM이 위임 범위에서 수정 작업을 승인·전달. 관계없는 조사 결과는 재사용 |
| 부족분과 추가 배정 | 기존 네 작업이 끝나도 고객 반응 관찰 조건이 남음. 담당 없는 조건과 필요한 시간을 표시. 사용자의 가용 시간 확인 후 관찰 작업을 새 계획에 배정 |
| 목표 마무리 | 인계는 `checked`로 이미 진행. 검증은 사람 승인 뒤에만 충족. 관찰까지 충족한 뒤 최종 목표 승인을 요청 |

초기 계획에서 고객 반응 관찰을 빠뜨린 것은 상태 모델 §7.1의 누락 시연이다. 실제 자유형식 계획에서는 처음부터 관찰 작업을 넣도록 제안하며, 일부러 누락을 만들지 않는다.

자유형식에서는 대본과 다른 목표·이름·기한·첨부를 입력한다. 농담과 제안, 상충하는 두 결정, 당사자 부재·거절, 가용 시간 누락, 변경 중 또 변경, 옛 결과 재제출, 중복 제출, 빈 모델 응답도 넣는다. 권한 밖 요청은 사람이 답할 때까지 해당 부분만 보류하고 독립 작업은 계속한다.

시연 기준 추천: 두 모드 각각 서로 다른 입력으로 전체 흐름을 3회 수행한다. 매회 사람의 초안·수정본에서 이어지는 인계 2건 이상, 조율에 따른 승인 계획 변경과 실행 반영 1건 이상을 확인한다. 중복 시작·무권한 변경·무효 산출물 인계·자기보고만으로 검증 충족은 0건이어야 한다. 테스트 사건 수만으로 성공을 대신하지 않는다.

인계 수는 “선행 입력 후 별도 시작 지시 없이 실행권을 얻고, 후속 세션의 실제 작업 시작까지 확인됨”을 원장으로 센다. 기동 요청이나 메시지 수락만으로 세지 않는다. 계획 변경 수는 승인·공유·당사자 확인·수정 결과가 연결된 경우만 센다. 사람 확인 횟수, 인계 뒤 되돌림, PM 개입 뒤 사람이 고친 횟수도 함께 기록한다.

수동 조율 시간은 같은 사례를 사람이 직접 배정·맥락 전달한 기준선과 비교한다. 키 입력·확인에 쓴 시간을 모델 대기 시간과 분리한다. 비교 실행 전에는 절감 효과를 주장하지 않는다.

## 11. 큰 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 잡담을 확정 결정으로 오해 | 분류는 후보만 만든다. PM의 별도 결정 또는 권한자의 명확한 답변이 있어야 반영한다. 원문·이유·되돌리기를 제공한다 |
| 너무 자주 끼어듦 | 같은 쟁점 묶기, 변경 없는 요약 생략, 카드 갱신, 당사자만 알림. 개입 뒤 무응답·취소도 관찰한다 |
| PM 권한 과잉·채팅 속 악성 지시 | Ensemble 쓰기는 서버 권한 검사. 세션은 전용 폴더·제한된 도구 권한으로 연결하고 원장·서버 비밀에 접근시키지 않는다. 제한 가능 여부를 먼저 확인하며 프롬프트만으로 강제했다고 보지 않는다 |
| 자동 행동이 계속 이어짐 | 사람의 새 지시나 명시적 확인 뒤 다음 확인까지 프로젝트당 시작·재개·수정 지시 합계 12회, 작업당 수정 지시 2회로 시작한다. 요약·모델 내부 단계는 제외. 둘 중 먼저 닿으면 신규 지시를 멈추고 한 번 알린다 |
| 짧은 시간에 턴·업데이트가 몰림 | 초기에는 프로젝트당 10분에 자동 신규 턴 6회로 제한한다. 초과 시 대기·알림, 중요 업데이트는 최신 변경으로 묶는다. 명시적 사람 확인으로도 속도 집계는 지우지 않는다 |
| 상한을 우회하거나 끝나던 작업을 잃음 | PM·Agent 메시지와 잡담은 카운터를 초기화하지 않는다. 진행 중 단계의 결과는 저장하되 다음 자동 지시는 막는다. 사람이 내용을 보고 재개하면 새 구간을 기록한다 |
| PM proxy 캐시·빈 응답 | 요청에 실제 계획·입력 버전과 논리 ID를 넣는다. 빈 응답은 의미를 바꾸지 않는 시도 ID로 1회 재시도. 캐시 우회는 확인 전까지 보장하지 않는다. 세션 공급자의 캐시 동작까지 같다고 가정하지 않는다 |
| 재시도로 실행이 두 번 일어남 | 업무 멱등 키는 작업·실행 세대·동작 ID. 세션 ID·수신 위치·업데이트 ID도 저장한다. 외부 기동 결과가 불명확하면 조회 없이 재기동하지 않는다 |
| LLM 일정 추정이 사실처럼 보임 | 코드가 계산한 값, 사람 입력, 임시 추정을 구분한다. 근거 없는 종료일을 확약하지 않는다 |
| PM의 잘못된 인계 판단 | 조건별 근거를 기록하고 부족하면 보완 요청. 오판이 확인되면 후속 작업을 영향 표시하고 입력부터 수정한다. 필요하면 수동 배정 모드로 전환한다 |
| Agent가 업데이트를 확인만 하고 무시 | 확인 응답 뒤 결과도 점검한다. 옛 세대 결과는 격리하며 최종 조립에서 무효 섹션을 걸러낸다 |
| 다른 대화의 맥락 혼합·중복 실행 | 세션을 프로젝트·채널·Agent로 나누고 같은 Agent는 한 턴씩 실행한다. 연결 신호가 끊겼다는 이유로 새 세션을 자동 기동하지 않는다 |
| 긴 추론을 실패로 오해·무한 재시도 | 단계 예상 시간과 진행 신호로 정체를 확인한다. 짧은 고정 제한만으로 종료하지 않는다. 재시도 횟수는 연결부와 PM이 공유하며 인증 실패 시 다른 런타임으로 자동 우회하지 않는다 |
| 오류나 첨부로 내부 정보 노출 | 채널에는 작업 영향·복구 방법만 알리고 상세 오류는 권한 있는 로그에 둔다. 로컬 주소·비밀을 가리고 첨부 경로의 접근 범위를 검사한다 |
| 검색·실행 환경을 과장 | 조사 Agent는 자료 출처와 실제 검색 여부를 표시한다. PM proxy의 검색 제한을 세션 전체의 제한으로 확대하지 않는다. 세션 도구의 이용 가능성은 확인 전 미정이다. 앱은 연결만 맡고 실행 샌드박스·CI 호스팅을 만들지 않는다 |

PM은 기존 Anthropic 호환 proxy와 기본 `claude-sonnet-5`를 쓴다. 실행 세션의 모델·인증·proxy 연결·사용량 제공 여부는 따로 확인한다. 비밀키는 맥락이나 원장에 넣지 않는다. 웹앱의 사람 전환은 로컬 시연용이며 실제 다중 사용자 인증을 대신하지 않는다.

## 12. 사용자에게 확인할 질문

| 질문 | 추천안 |
|---|---|
| PM이 승인할 변경의 범위를 어디까지 둘까요? | 시작 때 목표·완료 조건·기한·사람 시간·예산을 합의. 그 안의 작업 추가·분할·Agent 재배정은 PM 승인, 제품 약속 변경과 바깥 영향은 사람 승인. 검증 증거와 최종 목표 승인 규칙은 유지 |
| 실행 세션의 계정·모델·비용과 파일·도구 권한은 어떻게 제공되나요? | 사내 proxy 사용 가능 여부, 인증 방식, 사용량·동시 실행 제한, 폴더 격리·도구 제한을 확인. 승인된 실행 환경의 작업 전용 세션부터 연결하고 서버 비밀·외부 공개 권한은 주지 않음 |
| 가용 시간 입력과 PM 자동 진행 한도를 어떻게 둘까요? | 사람이 날짜별 가용 시간·소요 범위를 입력. 자동 지시는 확인 사이 프로젝트 12회·작업당 수정 2회, 자동 신규 턴은 10분에 6회부터 시작. 세션 내부 도구 횟수는 별도 한도를 확인 |
| 작업 중 Agent에게 온 메시지를 어디까지 바로 주입할까요? | PM이 확인한 계획 변경·현재 작업의 필수 정보만 즉시 주입. 나머지 질문은 현재 턴 뒤 답변하고 단순 참조는 실행하지 않음. 조율은 메인 채널 안의 스레드에서 진행 |
| 첫 시연의 성공 기준을 이 정도로 둘까요? | 두 모드 각각 입력을 달리해 3회, 매회 초안·수정본 후 자동 인계 2건·조율 후 실행 반영 1건 이상. 중복 시작·무권한 변경·무효 결과 인계·근거 없는 검증 충족은 0건 |
