# 최종 QA 카운터

## 제목 확인 기록

- 사용자에게 한 질문: "입력 방식 비교 문서의 맨 위에 표시할 제목을 알려 주세요." (선택지: 가상 카운터 입력 방식 비교 / 카운터 UI 입력 방식 및 키보드 접근성 비교 / 직접 입력)
- 사용자 답변: "문서 제목은 최종 QA 카운터입니다. 지금 문서 작성을 진행해 주세요."
- 반영 결과: 문서 제목을 답변 그대로 **최종 QA 카운터**로 정했습니다. 답변을 받기 전에는 최종본을 만들지 않았습니다.

## 문서 개요

이 문서는 UI 회귀 검증용 가상 카운터 프로젝트에 쓸 입력 방식을 비교합니다. 대상은 "0 표시, +1, 초기화"만 있는 최소 화면입니다. 프로젝트 방침에 따라 외부 조사, 외부 API, 실제 개인정보는 쓰지 않았습니다. 아래에 붙인 출처는 모두 **비교를 위해 정한 가상 문서명**입니다. 실제로 있는 문서도 아니고 직접 열어 본 자료도 아닙니다. 사용자의 가상 인터뷰 자료와 디자이너의 버튼 명세는 아직 받지 않았습니다. 두 자료가 들어오면 이 문서의 가정을 다시 확인해야 합니다.

비교한 입력 방식은 네 가지입니다.

| 기호 | 입력 방식 | 설명 |
|---|---|---|
| A | 마우스·포인터 클릭 | 화면의 "+1"과 "초기화" 버튼을 클릭하거나 탭합니다. |
| B | 키보드 Tab 이동 + Enter/Space | 포커스를 버튼으로 옮긴 뒤 표준 키로 누릅니다. |
| C | 전역 단축키 | 페이지 어디에서든 "+" 키나 "R" 키 같은 단축키로 조작합니다. |
| D | 숫자 직접 입력 필드 | 입력란에 값을 적어 카운터 값을 바꿉니다. |

## 가상 비교 근거

아래 근거는 모두 가상 문서에서 가져왔다고 가정한 내용입니다. 실제 측정값이 아니라 비교의 틀을 잡기 위한 가정입니다.

1. **클릭 방식(A)은 처음 쓰는 사람이 가장 빨리 이해합니다.** 가상 사용성 메모에 따르면 참여자 대부분이 따로 설명을 듣지 않고도 "+1" 버튼을 바로 눌렀습니다. 버튼에 붙은 글자가 하는 일을 그대로 알려 주기 때문입니다. 다만 같은 메모에는 버튼을 빠르게 연달아 누르면 브라우저에서 텍스트가 선택되거나 더블클릭으로 화면이 확대되는 일이 있었다는 기록도 있습니다. 그래서 회귀 검증 항목에 "연속 클릭 시 값이 누른 횟수만큼 정확히 늘어나는지"를 넣어야 합니다. (출처: 가상 문서 「카운터 사용성 관찰 메모 v0.1」)

2. **키보드 방식(B)은 접근성 기준을 맞추는 데 꼭 필요하고, 표준 버튼 요소만 쓰면 추가 구현 비용이 거의 없습니다.** 가상 접근성 점검표는 모든 기능을 키보드만으로 쓸 수 있어야 한다고 정합니다. HTML의 기본 button 요소를 쓰면 Enter와 Space 동작이 브라우저에서 자동으로 제공되므로, 직접 키 이벤트를 붙일 필요가 없습니다. 반대로 div나 span으로 버튼을 흉내 내면 Tab 순서, 키 입력, 역할 정보를 모두 손으로 채워야 하고, 이 부분이 회귀 결함이 가장 자주 생기는 곳으로 적혀 있습니다. (출처: 가상 문서 「접근성 점검표 초안 A-3」)

3. **전역 단축키(C)는 숙련 사용자에게는 빠르지만 충돌 위험이 큽니다.** 가상 내부 비교 노트는 단축키가 반복 테스트 시간을 줄여 준다고 평가합니다. 하지만 화면 낭독기나 브라우저 기본 단축키와 겹칠 수 있고, 입력란에 글자를 쓰는 동안 실수로 카운터가 바뀌는 문제도 지적합니다. 최소 기능 시연 화면에는 필수가 아니므로 이번 범위에서는 "선택 사항, 기본 비활성"으로 두자는 결론이 적혀 있습니다. (출처: 가상 문서 「입력 방식 내부 비교 노트 #2」)

4. **숫자 직접 입력(D)은 이번 범위와 맞지 않습니다.** 최종 시연 HTML에 필요한 기능은 0 표시, +1, 초기화뿐입니다. 직접 입력을 넣으면 음수, 소수, 빈 값, 아주 큰 수 같은 입력 검증 경우가 새로 생겨 회귀 검증 범위가 크게 늘어납니다. 가상 범위 정의서는 이 기능을 범위 밖으로 둡니다. (출처: 가상 문서 「시연 범위 정의서 r1」)

5. **종합 판단.** 기본은 A와 B를 함께 지원하고, C는 나중에 검토하며, D는 제외합니다. A와 B는 같은 button 요소 하나로 동시에 충족되므로 구현과 검증 비용이 가장 적습니다. 두 번째 하위 작업(버튼 동작 규칙)은 이 결론을 전제로 진행하면 됩니다. (출처: 가상 문서 「입력 방식 내부 비교 노트 #2」, 「시연 범위 정의서 r1」)

| 기준 | A 클릭 | B 키보드 | C 단축키 | D 직접 입력 |
|---|---|---|---|---|
| 배우기 쉬움 | 높음 | 보통 | 낮음 | 보통 |
| 접근성 기준 충족 | 단독으로는 부족 | 필수 | 보조 수단 | 별도 검증 필요 |
| 구현·검증 비용 | 낮음 | 낮음(표준 버튼 사용 시) | 중간 | 높음 |
| 이번 범위 포함 | 포함 | 포함 | 보류 | 제외 |

## 키보드 접근성·버튼 상태

이 섹션은 B 방식을 중심으로 키보드 사용자가 겪는 흐름과 버튼 상태별 표시 규칙을 정리합니다. 디자이너의 버튼 명세가 들어오면 색상과 모양 값은 그 명세로 바꿔야 합니다.

1. **포커스 순서.** Tab을 누르면 "+1" 버튼, 그다음 "초기화" 버튼 순서로 포커스가 이동해야 합니다. 화면에 보이는 순서와 Tab 순서가 같아야 하며, tabindex에 양수 값을 넣어 순서를 억지로 바꾸지 않습니다. 카운터 숫자는 조작 대상이 아니므로 포커스를 받지 않습니다. (출처: 가상 문서 「접근성 점검표 초안 A-3」)

2. **포커스 표시.** 포커스가 있는 버튼에는 눈에 잘 띄는 테두리가 보여야 합니다. 브라우저 기본 외곽선을 지우려면 같은 수준 이상의 대체 스타일을 넣어야 합니다. 가상 회귀 기록에 따르면 스타일을 정리하다 외곽선이 사라지는 일이 가장 흔한 회귀 결함이었습니다. 포커스 표시는 배경과 충분히 대비되어야 하고, 마우스로 클릭할 때만 보이지 않도록 :focus-visible을 쓰는 방식을 권장합니다. (출처: 가상 문서 「UI 회귀 결함 기록 2026-Q3」)

3. **키 동작.** "+1" 버튼에서 Enter나 Space를 누르면 값이 1 늘어납니다. "초기화" 버튼에서 누르면 값이 0이 됩니다. 키를 계속 누르고 있을 때 자동 반복으로 값이 여러 번 오르는지는 브라우저마다 다를 수 있으므로, 회귀 검증 시 기대값을 미리 정해 두어야 합니다. (출처: 가상 문서 「카운터 사용성 관찰 메모 v0.1」)

4. **값 변경 안내.** 화면 낭독기 사용자도 값이 바뀐 것을 알 수 있도록 카운터 숫자 영역에 aria-live="polite"를 붙입니다. 이렇게 하면 버튼을 누른 뒤 새 값이 읽힙니다. 너무 자주 읽혀 방해가 된다는 가상 인터뷰 의견이 있어, 숫자만 짧게 읽히도록 다른 문구를 섞지 않습니다. (출처: 가상 문서 「가상 사용자 인터뷰 요약 초안」. 실제 인터뷰 자료는 아직 받지 않았습니다.)

5. **버튼 상태 정의.**

| 상태 | 조건 | 표시 규칙(가정) |
|---|---|---|
| 기본 | 아무 조작 없음 | 기본 배경, 테두리 없음 |
| 호버 | 포인터가 버튼 위에 있음 | 배경을 한 단계 진하게 |
| 포커스 | 키보드로 포커스 이동 | 굵은 외곽선 표시 |
| 누름 | 클릭하거나 키를 누르는 중 | 배경을 더 진하게, 살짝 눌린 모양 |
| 비활성 | 값이 이미 0일 때의 "초기화" (선택 사항) | 흐린 표시, aria-disabled로 상태 전달 |

(출처: 가상 문서 「버튼 상태 표 초안 B-1」)

6. **비활성 상태 처리.** 값이 0일 때 "초기화" 버튼을 비활성으로 할지는 아직 정하지 않았습니다. disabled 속성을 쓰면 버튼이 Tab 순서에서 빠져서 키보드 사용자가 버튼이 있다는 사실을 모를 수 있습니다. 그래서 가상 점검표는 비활성으로 할 경우 aria-disabled="true"를 쓰고 포커스는 유지하는 방식을 권장합니다. 최종 결정은 디자이너 명세와 두 번째 하위 작업(버튼 동작 규칙)에서 정합니다. (출처: 가상 문서 「접근성 점검표 초안 A-3」, 「버튼 상태 표 초안 B-1」)

7. **회귀 검증 체크 항목.** ① Tab으로 두 버튼에 차례로 도달하는지 ② 포커스 외곽선이 보이는지 ③ Enter와 Space가 각각 한 번씩만 동작하는지 ④ 초기화 후 값이 0인지 ⑤ 값이 바뀔 때 화면 낭독기가 읽는지 ⑥ 상태별 스타일이 표대로 나오는지. (출처: 가상 문서 「UI 회귀 결함 기록 2026-Q3」)
