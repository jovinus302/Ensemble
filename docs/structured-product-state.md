## 1. 정의와 해결하려는 문제

Structured Product State는 **제품이 무엇이어야 하는지, 실제로 무엇이 구현되어 있는지, 둘 사이에 무엇이 다른지를 요구사항과 구현·검증 근거의 연결로 표현하는 상태 모델**이다.

PRD와 코드, 실행 화면이 따로 관리되면 요구사항이 실제로 충족되었는지 판단하기 어렵다. Ensemble은 이 관계를 유지하고 Agent가 차이를 해소하도록 하는 제품을 지향한다.

> Your PRD isn't a document. It's the desired state of your product.

이 문구는 제품 방향을 설명한다. 자연어 문서를 수정하는 것만으로 실행 중인 제품이 즉시 바뀐다는 의미는 아니다.

## 2. 논의에서 제안된 구조

| 계층 | 질문 | 주요 내용 |
| --- | --- | --- |
| Intent | 사용자가 무엇을 만들려는가? | 목적, 사용자 문제, 기대 결과 |
| Spec | 어떻게 동작해야 하는가? | Feature, Requirement, Constraint, Flow, Acceptance Criteria |
| Implementation | 무엇이 구현되어 있는가? | 파일, 컴포넌트, API, 데이터 모델, Route |
| Verification | 요구사항대로 동작하는 근거가 있는가? | 테스트 결과, 브라우저 관찰, 실행 증거 |
| Artifact | 사용자가 무엇을 경험하는가? | 화면, UI 요소, 실행 중인 애플리케이션 |

핵심은 저장 형식이 YAML인지 JSON인지가 아니라 참조 관계다. 하나의 Requirement에서 관련 Implementation, Artifact, Verification으로 이동할 수 있어야 한다. Graph는 이 관계를 보여주는 표현 방식 중 하나다.

## 3. Desired State와 Actual State

**Desired State**는 요구하는 제품 행동이다. **Actual State**는 저장소와 실행 결과를 관찰해 파악한 구현 상태다. 관찰하지 않은 동작은 확인되지 않은 상태로 남겨야 한다.

```text
Desired State ── 비교 ── Actual State
                  │
                  Δ
                  │
             Agent 작업 후보
                  │
             구현 → 검증
                  │
          관찰된 Actual State 갱신
```

`Δ = Desired State − Actual State`는 개념 표기다. 실제 차이 계산의 단위와 규칙은 후속 설계가 필요하다.

| 요구사항 | Desired | Actual 예시 | 남은 작업 |
| --- | --- | --- | --- |
| Google OAuth | 지원 | 미구현 | 구현 및 검증 |
| Password Reset | 지원 | 인수 조건 검증 완료 | 해당 관찰 범위에서 차이 없음 |
| Dark Mode | 지원 | 일부 화면만 적용 | 누락 화면 구현 및 검증 |

코드 존재, 구현 진행, 검증 결과는 서로 다른 정보다. 파일이 생겼거나 테스트 일부가 통과했다는 이유만으로 요구사항 전체를 충족했다고 표시하면 안 된다.

## 4. 사용자 경험: 요구사항에서 근거까지

사용자가 `Google OAuth` 요구사항을 선택하면 다음 정보를 함께 확인하는 경험을 제안한다. 아래 경로와 결과는 설명용이며 실제 저장소의 구현 증거가 아니다.

```text
Requirement: auth-google
  기대 행동: Google 계정으로 로그인할 수 있다.

Implementation
  src/auth.ts
  src/components/GoogleLogin.tsx
  /api/auth/google

Artifact
  /login → Google Login Button

Verification
  버튼 표시: 통과
  인증 화면 이동: 통과
  Callback 이후 로그인 완료: 미검증

판정: 일부 검증됨. 전체 동기화 완료로 표시하지 않음.
```

이 연결이 있으면 PRD는 요구사항과 관련 코드를 찾고, 실행 결과를 검토하는 진입점이 된다.

## 5. Agent 실행과 상태 전이

```text
사용자 요구사항 변경
  → Desired State 갱신
  → Actual State와 차이 계산
  → 관련 요구사항·파일·화면·테스트 파악
  → Agent 구현
  → 테스트 및 브라우저 검증
  → 구현 상태와 검증 근거 갱신
  → 해당 요구사항의 동기화 여부 판정
```

사용자 편집으로 먼저 바뀌는 것은 Desired State다. 구현과 검증에는 시간이 필요하며, 실행 중에는 Desired와 Actual이 다를 수 있다. 차이 계산의 즉시성도 관찰 정보의 최신성과 계산 방식에 달려 있다.

대화의 `missing → requested → implementing` 같은 표현은 서로 다른 상태 차원을 섞을 수 있다. 문서화 과정에서 다음 분리를 제안하며, 최종 enum과 전이 규칙은 미정이다.

| 구분 | 표현할 정보 예시 |
| --- | --- |
| 요구 상태 | 어떤 행동을 요구하는가 |
| 구현 상태 | 미구현, 부분 구현, 구현됨, 확인 불가 |
| 실행 상태 | 대기, 실행 중, 실패, 완료 |
| 검증 상태 | 미검증, 일부 검증, 통과, 실패, 오래된 근거 |
| 동기화 판정 | 현재 요구사항과 유효한 관찰 근거가 일치하는가 |

`Synced`는 정해진 요구사항과 관찰 범위에 대한 판정이어야 한다. 제품 전체에 결함이 없다는 보증으로 사용하지 않는다.

## 6. Terminal, Browser, ttyd의 위치

참조 대화는 Terminal을 명령 실행·코드 변경·테스트의 작업면으로, Browser를 실행 화면의 관찰·조작·검증 작업면으로 설명한다. 두 환경은 같은 요구사항을 구현하고 확인하는 과정에 연결된다.

```text
              Product State
                    │
                  Agent
             ┌──────┴──────┐
          Terminal       Browser
             │              │
        구현·테스트      화면·행동 검증
             └──────┬───────┘
              상태와 증거 갱신
```

대화에서 ttyd는 실제 CLI 프로세스와 웹 터미널을 연결하는 구현 후보로 소개되었다. Product State의 저장소나 브라우저 검증 엔진 역할은 아니다. 도입 여부와 운영 구성을 이 문서에서 확정하지 않는다.

차별화 가설은 Terminal·Browser 패널의 존재보다 **요구사항 → 실행 → 검증 → 상태 갱신의 지속적인 연결**에 있다. 경쟁 제품 대비 차별성은 별도 조사와 사용자 검증이 필요하다.

## 7. MVP 데이터 모델 제안

| 개체 | 최소 정보 제안 | 연결 대상 |
| --- | --- | --- |
| Product | ID, 목적 | Feature |
| Feature | ID, 이름 | Requirement, Flow |
| Requirement | ID, 설명, 인수 조건 | Surface, Implementation, Verification |
| Flow | 사용자 행동 순서 | Requirement, Surface |
| Surface | 페이지 또는 컴포넌트, 식별 정보 | Requirement, 실행 Artifact |
| Implementation | 파일·API·데이터 모델 참조 | Requirement |
| Verification | 검증 대상, 방법, 결과, 근거 참조 | Requirement, Implementation, Artifact |

추가 설계 제안: 검증 근거가 어느 요구사항 버전, 코드 revision, 실행 환경에 해당하는지 기록한다. 그래야 변경 이전의 통과 결과를 현재 상태의 증거로 재사용하는 오류를 피할 수 있다. 이 필드는 원대화의 확정 사양이 아니다.

첫 검증 범위는 로그인 기능 하나로 제한할 수 있다. 요구사항 등록, 구현 연결, 검증 결과 연결, 차이 표시까지 한 사이클을 관찰한다. 자동 코드 분석이나 모든 화면의 양방향 편집은 첫 사이클의 필수 조건으로 확정하지 않는다.

## 8. 양방향 변경: 후속 확장 후보

| 변경 출발점 | 제안된 흐름 | 결정이 필요한 부분 |
| --- | --- | --- |
| PRD | Desired 변경 → 구현 → 검증 | 실행 시작 조건과 승인 범위 |
| Code | Actual 변경 감지 → Spec 반영·구현 되돌리기·무시 제안 | 감지 정확도, 선택 권한, 무시의 지속 범위 |
| Artifact | UI 요소 선택 → 연결 요구사항 탐색 → Desired 변경 | 요소와 요구사항의 매핑, 여러 후보 처리 |

직접 변경된 코드를 감지했다고 해서 사용자 의도가 바뀌었다고 단정할 수 없다. Spec 반영과 코드 되돌리기는 선택 가능한 제안으로 남기며 자동 정책으로 확정하지 않는다.

## 9. 미결정 사항과 관찰 계획

| 미결정 사항 | 확인할 질문 또는 실험 |
| --- | --- |
| 차이 계산 | 누락, 부분 구현, 미검증을 어떤 근거로 구분하는가? |
| 연결 생성 | 사람이 지정할지, Agent가 제안할지, 자동 분석할지? 잘못된 연결을 어떻게 수정하는가? |
| 근거 유효성 | 요구사항이나 코드가 바뀌면 어떤 검증 결과를 만료시키는가? |
| 동시 변경 | 실행 중 요구사항이 바뀌면 기존 작업을 중단할지, 구버전 결과로 보존할지? |
| 실패와 복구 | 실패 원인과 부분 변경을 어떻게 보여주고 재시도하는가? |
| 권한 | 상태 갱신, 코드 변경, 되돌리기, 배포의 권한 경계는 무엇인가? |
| 사용자 가치 | 사용자가 요구사항의 구현 여부와 미검증 이유를 실제로 더 쉽게 판단하는가? |

개념 검증에서는 정상 완료뿐 아니라 Callback 미검증, 검증 실패, 실행 중 요구사항 수정, 외부 코드 변경을 관찰한다. 성공 기준은 작업 완료 표시 자체가 아니라, 사용자가 현재 충족 여부와 남은 차이를 근거와 함께 정확히 확인할 수 있는지다.

## 10. 이번 문서화 작업의 명제와 검토

이 절은 제품 사양이 아니라 문서 작성 범위와 검증 기록이다.

- **확인된 의도:** 참조 대화 내용을 문서화한다.
- **해석:** 가장 최근에 구체화한 Structured Product State를 중심으로 정리하고 ttyd 논의를 실행 환경의 맥락으로 포함한다.
- **기대 결과:** 독자가 개념, 계층, Desired/Actual 차이, 실행 흐름, MVP 제안과 미결정 사항을 구분할 수 있다.
- **불변 조건:** 대화의 제안을 구현 사실이나 확정 정책으로 바꾸지 않는다. PRD 변경을 즉각적인 구현 완료로 표현하지 않는다.
- **검증 계획:** 원대화의 주요 주제와 대조하고 예시·추가 제안 표시, 문서 형식과 Git diff를 확인한다.
- **사전 가설 검토 — SOUND:** 요청에 맞는 문서 변경이며, 실행 기능이나 제품 정책을 도입하지 않는다.
- **분류 — COMMITTED CHANGE:** 문서화 변경을 뜻한다. 본문의 제품 구상에 대한 채택 결정을 의미하지 않는다.

실행 검토: 원대화의 5계층, 요구사항 연결, Desired/Actual, Agent 흐름, Terminal·Browser, MVP 개체, 양방향 변경을 각각 2~8절에 대응시켰다. 상태 차원 분리와 근거 버전 추적은 추가 제안으로 표시했다. 실제 제품의 기능 검증은 이 문서화 작업에 포함되지 않는다.

구현 검토 — **PASS**: 요청한 개념 문서를 작성했고, 주요 논의와 미결정 사항을 포함했으며, 추가 해석을 표시했다. 애플리케이션 동작과 기존 문서는 변경하지 않았다. UTF-8 본문 확인과 staged diff 공백 검사를 통과했다.
