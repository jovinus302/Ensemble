> 기준: [이슈 #62](https://github.com/jovinus302/Ensemble/issues/62) "10/7 소장님 보고", 보고일 **2026-10-07(수)**. 스토리 원천은 [S27 스토리 브리프](brief.md)이며, 구현 현황은 PR #64가 병합된 뒤의 `main@605521b` 코드로 2026-10-05에 확인했다. `/demo/pm-coordination`·`/demo/design-to-code`와의 차이는 [데모 안내](../../README.md)를 참고한다.
> 이 문서는 **현재 구현**과 **데모(시뮬레이션)**와 **제안**을 구분한다. 데모 화면에 보이는 것이 곧 제품 기능이라는 뜻이 아니다.

## 1. 목적과 실행 방법

**한 줄 목적:** 앙상블이 팀의 컨텍스트·도구·의사결정·결과물을 연결하는 **공유 업무 기반**이라는 포지셔닝을, 마케팅팀 한 사례(S27 사전예약 소재 제작)로 5단계에 걸쳐 보여 주고, 각 장면이 어떤 해자 가설을 지지하는지와 그 가설을 어떻게 검증할지를 함께 제시한다.

> 포지셔닝 문장(이슈 #62): 앙상블은 팀의 컨텍스트, 도구, 의사결정과 결과물을 연결해 사람과 에이전트가 협업을 이어갈 수 있게 하는 공유 업무 기반이다. 협업은 팀이 일하는 다양한 채널에서 시작하고, 그 과정의 근거·결정·결과물은 앙상블에 연결되어 다음 작업에 활용된다.

### 실행

```sh
cd app
npm run dev
```

브라우저에서 `http://localhost:3000/demo/marketing-campaign`을 연다.

| 키 | 동작 |
|---|---|
| `→` / `Space` | 다음 장면(beat) |
| `←` | 이전 장면 |
| `Home` | 처음(제목 화면)으로 |
| `N` | 발표 노트(장면별 발표 문장) 보이기/숨기기. 기본은 숨김이며 화면에는 큰 헤드라인만 나온다 |

- **API 키·모델·로그인이 필요 없다.** 기존 Ensemble 앱의 `ENSEMBLE_PM_RUNTIME` 설정과 무관하게, `/demo/marketing-campaign` 화면은 미리 작성된 시나리오 데이터만 재생한다. 공유 계약은 `app/demo/scripted/marketing-campaign/types.ts`에 있다.
- **로컬 스크립트형 시연이다.** Slack·녹스 미팅·모델(LLM)·Ensemble 서버 API를 **호출하지 않는다.** 화면의 "팀 메신저"·"화상 미팅"은 실제 서비스가 아니라 중립 스타일의 시뮬레이션이며 "(시뮬레이션)"으로 표기된다.
- 화면의 대화·카피 문구·수치는 모두 가상이다. 해자 지표 값은 **시나리오 가정**이며 측정 결과가 아니다.
- 화면에 등장하는 기능마다 구현 현황 라벨(현재 구현 / 데모 가능 / 추가 개발 필요)이 붙는다. 라벨의 근거는 아래 [§3 구현 현황 표](#3-구현-현황-표)다.

## 2. 발표 스크립트 (5단계)

장면 수(beat)는 코드에서 조정될 수 있으므로 **단계 기준**으로 적는다. 등장인물: 김하린(마케팅 리드, 결정권자), 박준호(퍼포먼스 마케터), 이서아(브랜드 매니저), 정민재(법무·광고 심의), Ensemble 에이전트, 카피 Agent.

### 단계 1. 미팅에서 결정 — "S27 캠페인 킥오프" 화상 미팅 (10/1, 시뮬레이션)

- **화면:** 화상 미팅 화면에서 하린·준호·서아가 방향을 논의하고, 앙상블 에이전트가 참석자로 함께 있다. 결정 3건(핵심 메시지 "밤에도 선명한 인물 사진", 타깃·채널 2030 메타 피드+숏폼, 제약 경쟁사 비교 금지·수치 각주·가격 엠바고)이 허브에 결정 노드로 생기고, 각 결정이 브랜드 가이드 v3·S26 성과 리포트·제품 스펙·광고 표기 체크리스트에 근거선으로 연결된다. 마지막에 앙상블이 "결정 3건을 기록했고, 근거 자료 4건과 연결했습니다"라고 말한다.
- **발표 멘트:** "협업은 앙상블 화면이 아니라 팀이 원래 일하던 미팅에서 시작합니다. 앙상블 에이전트는 미팅에 함께 있으면서 결정이 무엇이고 무엇을 근거로 했는지를 기록합니다. 중요한 건 결정 문장만 남는 게 아니라, 그 결정이 어떤 자료에 기대고 있는지가 함께 연결된다는 점입니다. 참고로 미팅 연동 자체는 아직 개발 전이고, 결정을 기록하는 구조는 지금 앱에 있습니다."
- **지지하는 해자 가설:** 기술적(대화·근거·결정의 연결 보존). 구현 라벨: `cap-meeting` 추가 개발 필요, `cap-decision` 현재 구현(단, 미팅 캡처 경로는 제외).

### 단계 2. 슬랙에서 요청 — `#s27-launch` 팀 메신저 (10/2, 시뮬레이션)

- **화면:** 준호가 "@Ensemble 킥오프 결정대로 메타 피드 소재 3종이랑 숏폼 스크립트 하나 초안 부탁해요."라고 쓴다. 앙상블은 답하면서 스스로 이어받은 것(킥오프 결정 3건, 브랜드 가이드 v3, S26 리포트)을 칩으로 밝히고 "가격은 엠바고라 넣지 않겠습니다"라고 덧붙인다. 허브에 요청 노드가 생긴다.
- **발표 멘트:** "채널이 미팅에서 메신저로 바뀌었지만 준호는 배경을 다시 설명하지 않습니다. 앙상블이 어제 미팅의 결정과 팀 자료를 먼저 꺼내 와서, 무엇을 근거로 일할지 요청자에게 보여 줍니다. 가격 엠바고처럼 미팅에서 정한 제약도 요청 문장에 없었지만 지켜집니다."
- **지지하는 해자 가설:** 경험적(채널이 바뀌어도 재설명 없음). 구현 라벨: `cap-slack` 추가 개발 필요, `cap-crosschannel` 데모 가능.

### 단계 3. 맥락으로 드래프트

- **화면:** 도구 실행 2건이 허브에 기록된다 — "S26 성과 리포트 조회"와 "브랜드·법무 표기 검사(금지 표현 0건, 각주 필요 1건 처리)". 카피 Agent가 **S27 사전예약 소재 v1.0**(메타 피드 A/B/C + 15초 숏폼 스크립트)을 만들고, 앙상블이 `#s27-launch`에 근거 칩이 달린 결과물 카드로 게시한다.
- **발표 멘트:** "앙상블은 직접 다 쓰지 않고 실행 에이전트에게 일을 맡기는데, 이때 결정·자료·제약이 함께 넘어갑니다. 어떤 도구를 어떤 목적으로 실행했고 무엇을 처리했는지도 결과물 옆에 남습니다. 결과물은 메신저로 돌아가지만, 원본과 연결 관계는 앙상블에 남습니다."
- **지지하는 해자 가설:** 기술적(도구 실행·아티팩트 연결 보존). 구현 라벨: `cap-tools` 데모 가능, `cap-artifact` 현재 구현.

### 단계 4. 근거·결정 연결 확인 — 앙상블 허브

- **화면:** 허브로 전환해 v1.0을 선택하면 상류 추적이 펼쳐진다: 결과물 ← 요청 ← 결정 3건 ← 공유 자료, 그리고 사용한 도구 실행. 섹션(예: 메타 피드 B)마다 근거 노드가 표시된다.
- **발표 멘트:** "'이 문장은 왜 이렇게 쓰였나'라는 질문에 회의록이나 스레드를 뒤지지 않고 섹션에서 결정과 자료까지 바로 따라갈 수 있습니다. 이 화면이 앙상블이 '공유 업무 기반'이라고 말하는 이유입니다. 다만 이 섹션 단위 그래프는 지금은 데모 화면이고, 앱에는 이벤트 단위의 근거 연결이 일부 있습니다."
- **지지하는 해자 가설:** 기술적(버전·출처·근거 추적). 구현 라벨: `cap-provenance` 데모 가능, `cap-ledger` 현재 구현.

### 단계 5. 다른 팀원이 이어서 수정 — `#brand-review` (10/3, 다른 채널·다른 사람, 시뮬레이션)

- **화면:** 민재(법무)가 "B안 배터리 문구는 측정 조건 각주 필요, '압도적'은 최상급이라 삭제"를 요청하고, 서아(브랜드)가 "법무 의견 반영 + 톤을 더 따뜻하게, 숏폼 첫 3초는 인물 클로즈업"을 요청한다. 서아는 v1이 어디 있는지, 킥오프에서 뭘 정했는지 말하지 않는다. 앙상블이 최신 버전 v1.0과 킥오프 결정을 스스로 찾아 **v1.1**을 만든다(각주 추가·최상급 제거·톤 조정·숏폼 오프닝 변경, 결정 3건 유지). `#brand-review`에 v1.1 카드를 올리고, 원래 요청자 준호에게 `#s27-launch` 스레드로 "v1.1로 갱신됨"을 알린다. 마지막으로 허브에서 v1.1을 선택하면 v1.0과의 변경점, 피드백 2건, 결정 3건이 모두 연결된 그래프가 보이고, 이어서 해자 지표 표와 구현 현황 표가 나온다.
- **발표 멘트:** "이번에는 채널도 사람도 바뀌었습니다. 담당자가 바뀌어도 아무도 배경을 다시 설명하지 않고, 옛 버전으로 작업하는 실수 없이 최신 v1.0과 기존 결정을 이어받아 v1.1이 나옵니다. 법무 피드백은 이번 한 번 쓰고 사라지지 않고 결정 이력과 함께 다음 작업의 자산으로 남습니다. 이게 실제로 재설명과 재작업을 줄이는지는 아래 검증 계획으로 확인하겠습니다."
- **지지하는 해자 가설:** 경험적(담당자가 바뀌어도 이어받음), 축적(결정 이력·피드백 자산화). 구현 라벨: `cap-crosschannel` 데모 가능, `cap-artifact` 현재 구현, `cap-permission` 추가 개발 필요(권한별 맥락 제공은 이 장면에서 다루지 않음).

## 3. 구현 현황 표

라벨 정의(`app/demo/scripted/marketing-campaign/types.ts`의 `Availability`):

- **현재 구현** — 지금 Ensemble 앱(`app/`)에 코드로 존재한다. 근거 경로를 함께 적는다.
- **데모 가능** — 이 S27 스크립트 시연에서만 보여 준다. 실제 데이터와 연결되어 있지 않다.
- **추가 개발 필요** — 만들어지지 않았다. 데모는 시뮬레이션일 뿐이다.

| capability id | 내용 | 브리프 초안 | 최종 라벨 | 근거 한 줄 | 근거 경로 |
|---|---|---|---|---|---|
| `cap-meeting` | 녹스 미팅에 에이전트 초대·결정 캡처 | 추가 개발 필요 | **추가 개발 필요** | 미팅 서비스 연동 코드가 저장소에 없고, 결정은 앙상블 채널 대화에서만 기록된다. | — |
| `cap-slack` | 슬랙 채널에서 @Ensemble 호출 | 추가 개발 필요 | **추가 개발 필요** | 채널 계층은 `ChannelAdapter` 인터페이스만 정의하고 구현체는 자체 웹앱뿐이며, intent와 MVP 아키텍처 문서도 실제 Slack 연동이 아님을 명시한다. | (인터페이스만) `app/packages/channel/src/index.ts` |
| `cap-channel` | 앙상블 자체 채널에서 사람·PM·에이전트 대화 | 현재 구현 | **현재 구현** | 프로젝트 채널과 작업별 스레드에서 사람 메시지(`message_recorded`), 에이전트 응답(`reply_recorded`), PM 발화(`pm_spoke`)가 기록·표시된다. | `app/packages/core/src/events.ts`, `app/apps/web/components/Message.tsx`, `app/apps/web/components/Composer.tsx`, `app/packages/orchestrator/src/coordination.ts` |
| `cap-decision` | 결정 요청·기록 | 현재 구현 | **현재 구현** | 대화에서 확정된 결정(`decision_recorded`, 근거 메시지 id 포함)과 사람에게 묻는 결정 요청(`decision_requested`/`decision_resolved`)·결정 카드가 있다. | `app/packages/core/src/decision-requests.ts`, `app/packages/orchestrator/src/decision-flow.ts`, `app/apps/web/components/DecisionRequestCard.tsx` |
| `cap-ledger` | 이벤트 ledger로 대화·결정·작업 기록 보존 | 현재 구현 | **현재 구현** | 모든 상태는 이벤트 원장의 투영이며 SQLite에 저장되어 재시작 시 복원된다. | `app/packages/core/src/ledger.ts`, `app/packages/core/src/projection.ts`, `app/packages/store/src/sqlite.ts` |
| `cap-artifact` | 결과물 첨부·revision·검토 | 현재 구현 | **현재 구현** (보정 참조) | 첨부(`attachment_recorded`), 결과 제출(`result_submitted`), PM 인계 검토(`handoff_reviewed`), 보완 요청(`revision_requested`)과 확인/다시 맡기기 UI가 있다. | `app/packages/orchestrator/src/handoff.ts`, `app/packages/orchestrator/src/session-runner.ts`, `app/apps/web/components/TaskResolution.tsx`, `app/apps/web/app/api/[...path]/route.ts` |
| `cap-provenance` | 섹션 단위 근거 추적 그래프 | 데모 가능 | **데모 가능** (보정 참조) | 섹션→결정→자료 그래프는 S27 시연에만 있다. 앱에는 이벤트 단위 근거 연결(결정·계획의 `sourceMessageIds`, 에이전트 입력 항목별 `sourceId`, 인계 검토의 `evidence`)만 있다. | (부분 근거) `app/packages/orchestrator/src/context.ts` |
| `cap-crosschannel` | 다른 채널·다른 사람 요청에서 최신 버전·결정 자동 선택 | 데모 가능 | **데모 가능** (보정 참조) | 외부 채널 간 이어받기와 결과물 버전 자동 선택은 시연에만 있다. 앱에서는 같은 프로젝트 안에서 작업 시작 시 확정 결정·선행 작업의 확인된 결과가 컨텍스트로 자동 주입된다. | (부분 근거) `app/packages/orchestrator/src/context.ts` |
| `cap-tools` | 팀 공유 도구 실행 기록 | 데모 가능 | **데모 가능** | 원장은 에이전트 turn 단위(`session_linked`, `turn_observed`)만 기록하고 개별 도구 호출은 기록하지 않는다. "팀 공유 도구" 개념은 없다. | — |
| `cap-permission` | 팀·사용자 권한별 맥락·도구 제공 | 추가 개발 필요 | **추가 개발 필요** | 인증이 없고(MVP 범위), 권한별로 맥락·도구를 나누는 기능이 없다. 있는 것은 계획 변경의 승인 권한 규칙뿐이다. | (다른 개념) `app/packages/core/src/authority.ts` |

### 브리프 대비 보정

라벨 자체를 바꾼 항목은 없다. 다만 다음 다섯 항목은 라벨만 보면 오해할 수 있어 단서를 단다. 데모 화면의 라벨은 브리프 초안 그대로 두어도 되지만, 발표 중 질문이 나오면 아래처럼 답한다.

1. **`cap-artifact` — 현재 구현, 단 "버전" 의미가 다르다.** 앱의 revision은 같은 작업에 대한 **재제출**(새 `resultId`)과 보완 요청이다. 데모의 v1.0→v1.1처럼 결과물 문서가 `supersedes` 관계와 변경점 목록을 갖는 **버전 체인**과 비교 화면은 앱에 없다(데모 가능 수준).
2. **`cap-provenance` — 데모 가능, 단 기반은 일부 현재 구현.** 섹션 단위 그래프는 없지만, 결정·계획·작업 브리프가 근거 메시지 id를, 에이전트 입력의 각 항목이 `sourceId`를 가진다. "근거 추적이 전혀 없다"도, "섹션 단위로 된다"도 사실이 아니다.
3. **`cap-crosschannel` — 데모 가능, 단 앙상블 내부에서는 부분 구현.** 같은 프로젝트에서 다음 작업이 시작될 때 확정 결정과 선행 결과를 자동으로 넘기는 것은 현재 구현이다. 외부 채널(Slack·미팅)에서 들어온 다른 사람의 요청에 대해 최신 결과물 버전을 고르는 것은 시연뿐이다.
4. **`cap-permission` — 추가 개발 필요, 단 "권한" 단어 충돌 주의.** 앱의 `authority`는 "PM이 어떤 계획 변경을 스스로 적용할 수 있는가"를 정하는 **결정 위임 규칙**이다. 사용자·팀별 접근 제어나 맥락·도구 범위 제한과는 다른 개념이다.
5. **`cap-decision` 단계 1 표기.** 결정 기록 구조는 현재 구현이지만, 단계 1처럼 **미팅에서** 결정을 캡처하는 경로는 `cap-meeting`(추가 개발 필요)에 속한다.

## 4. 해자 가설과 검증 계획

해자는 **입증할 가설**이다. 아래 "앙상블 시나리오" 열은 데모의 **시나리오 가정**이며 측정값이 아니다. 지금까지 이 가설을 입증한 측정은 없다.

| id | 지표 | 기존 방식 | 앙상블 시나리오 (시나리오 가정) | 측정 방법 |
|---|---|---|---|---|
| `m-reexplain` | 배경 재설명 횟수 | 채널·담당자가 바뀔 때마다 요청자가 배경을 다시 설명 | 0회 — 에이전트가 결정·자료를 먼저 꺼냄 | 인수인계 실험: 같은 과제를 기존 도구 조건과 앙상블 조건으로 나눠, 담당자 교체 후 요청 메시지에서 배경 설명 발화(이전 결정·자료를 다시 서술한 문장) 수를 두 명이 독립 코딩해 비교 |
| `m-search` | 자료 탐색·전달 | 링크·파일을 찾아 붙여넣기 | 에이전트가 근거를 인용 | 요청 시작부터 작업자가 필요한 자료를 확보할 때까지의 시간, 사람이 직접 붙여넣은 링크·파일 수를 화면 기록으로 측정 |
| `m-rework` | 인수인계 후 재작업 | 옛 버전·결정 누락으로 재작업 | 최신 버전·결정 자동 연결 | 후속 수정 과제에 일부러 구버전·변경된 결정을 섞어 두고, 결과물이 잘못된 버전·결정을 기반으로 한 비율과 그로 인한 재작업 횟수를 집계 |
| `m-trace` | 결정 근거 추적 | 회의록·스레드 수동 검색 | 섹션→결정→자료 클릭 추적 | "이 문장의 근거는?" 질문 세트(정답 근거 사전 고정)에 답하는 시간과 정답률을 두 조건에서 비교 |

**축적 해자에 대한 단서:** 결정 이력·피드백이 쌓인다는 것만으로는 해자가 아니다. 위 `m-reexplain`·`m-rework`가 과제를 반복할수록 줄어드는지(2회차·3회차 비교)를 보여야 "자산화"라고 말할 수 있다.

## 6. 예상 질문과 답

**Q1. 슬랙 연동 지금 되나?**
안 된다. 지금 앱은 자체 Slack형 웹 채널이고, 채널 계층에 연동용 `ChannelAdapter` 인터페이스만 있다(`app/packages/channel/src/index.ts`). 오늘 화면의 Slack·미팅은 시뮬레이션이다. 연동은 별도 이슈로 범위와 인증을 정해야 한다.

**Q2. 기존 Slack AI·Notion AI·Copilot과 뭐가 다른가?**
저장소가 근거로 말할 수 있는 차이는 구조다. 앙상블은 대화·결정·작업·결과물·인계 검토를 하나의 이벤트 원장에 기록하고, 다음 작업에 확정 결정과 선행 결과를 출처 id와 함께 넘긴다(`app/packages/orchestrator/src/context.ts`). 경쟁 제품이 이것을 하지 못한다는 비교 조사는 이 저장소에 없으므로 **가설**이다. 우리 가설은 "특정 도구 안의 AI"가 아니라 "여러 채널에 흩어진 근거·결정·결과물을 잇는 공유 기반"이라는 위치가 다르다는 것이다.

**Q3. 오늘 화면 중 실제로 동작하는 것은?**
`/demo/marketing-campaign` 화면 자체는 스크립트 재생이다. 그 밑에 깔린 개념 중 채널 대화, 결정 기록·요청, 이벤트 원장, 결과물 첨부·검토·보완 요청은 기존 Ensemble 앱에 현재 구현으로 있다(§3 표). 섹션 단위 근거 그래프, 외부 채널 간 이어받기, 도구 실행 기록은 데모 가능, Slack·미팅·권한은 추가 개발 필요다.

**Q4. 해자가 있다는 증거가 있나?**
아직 없다. 지표의 "0회" 같은 값은 시나리오 가정이다. §4의 인수인계 실험으로 재설명·재작업 감소를 측정하자는 것이 이번 제안이다.

**Q5. 결정이나 근거를 에이전트가 잘못 기록하면?**
현재 앱에서는 확정 결정(`decision_recorded`)과 사람에게 묻는 결정 요청이 구분되고, 계획 변경은 승인 권한 규칙(`app/packages/core/src/authority.ts`)에 따라 결정권자 확인을 거친다. 원장은 이벤트를 덧붙이는 방식이라 이력이 남는다. 미팅에서 자동 캡처한 결정을 사람이 확인·수정하는 흐름은 미팅 연동과 함께 설계해야 한다.

**Q6. 마케팅 말고 다른 팀에도 쓰이나?**
§5의 세 팀은 시나리오 제안이다. 프로덕트 디벨롭먼트팀이 현재 앱의 작업·인계 흐름과 가장 가깝고, 자금 운용사·정부부처는 권한·보안 요구가 커서 `cap-permission`이 선행되어야 한다는 것이 **가설**이다.

**Q7. 다음에 무엇을 하나?**
아래 후속 이슈 후보 중 하나를 골라 범위를 좁히고, 해자 지표 한 개(우선 `m-reexplain`)를 실제 팀 과제로 측정하는 것을 제안한다.

### 후속 실행 이슈 후보

각 항목은 별도 이슈로 연다.

1. **Slack 연동** — `ChannelAdapter` 구현, 봇 설치·인증, @Ensemble 호출과 스레드·카드 게시, 외부 메시지 출처(채널·작성자·링크)를 원장에 보존.
2. **녹스 미팅 연동** — 미팅 참여·전사 수집 방식, 결정 후보 추출과 사람 확인 흐름(`decision_recorded`로 확정 전 단계), 개인정보·녹음 동의.
3. **Provenance 저장 모델** — 결과물 버전 체인(`supersedes`·변경점), 섹션 단위 근거 링크, 도구 실행 기록 이벤트, 외부 채널 출처를 원장 이벤트로 어떻게 표현할지 설계.
4. **권한** — 사용자 인증, 팀·역할별 맥락·도구 접근 범위, 기존 `authority`(결정 위임)와의 관계 정리.
5. **해자 검증 실험** — §4 지표 중 하나로 인수인계 실험 프로토콜 작성(조건·판정 기준·참여자·실행 범위를 먼저 정한다).
